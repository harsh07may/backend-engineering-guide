Capstone Project

Fourteen chapters built the orders API one piece at a time, each piece introduced by the chapter that needed it. This one hands the same service back as a specification and asks you to build it from an empty directory, choosing the techniques yourself.

The brief

Reading a technique and reaching for it are different skills. Everything so far was prompted: the chapter named the problem before showing the answer. Nothing below names it.

You are building one service, the orders API for a small shop. Customers browse a catalogue, place orders against stock, and read their own order history. Three properties have to hold while they do it: stock never goes negative, a resubmitted order is not placed twice, and a dependency failing does not take the service down with it.

Those three are the whole exercise. Everything else is the scaffolding they need.

Rules

  • Start from an empty directory. The only part worth copying is Project setup.
  • Build in the milestone order below, and run the service at the end of each milestone. A milestone that has not run is not finished.
  • Where a requirement is checkable, write the check before the code. Unit Testing covers the mechanics.
  • Open a linked chapter when you are stuck, after you have tried. The links are an index, not a reading order.
In scopeLeft out, deliberately
Products, orders, users, authenticationA user interface of any kind

One deployable serviceA second service, until the stretch goals

The shape is a monolith, and that is the right starting point for one developer and one database. Trade-offs argues the case; the stretch goals break it apart once there is something to break.

Common mistake Writing all seven milestones before running any of them. The first time you start the service you want one new thing to be wrong, not seven.

The data you must store

Four tables carry the service. The constraints matter more than the columns: each one is a rule the database keeps even on the day your code forgets to.

TableHoldsThe database must enforce
usersEmail, hashed password, when they joinedOne account per email
productsName, price, stock on handPrice and stock never go below zero
ordersOwner, status, total, whenStatus is one of `pending`, `paid`, `shipped`, `cancelled`; the owner is a real user
order_itemsOne row per product in an orderQuantity above zero; deleting an order deletes its items

Two decisions are worth making deliberately, because both are expensive to reverse:

  • Money is an integer count of cents. Not a float. `0.1 + 0.2` is not `0.3` in binary floating point, and a cent lost per order compounds.
  • An order item stores the price it was bought at. Not a join to the product. A price change next week must not rewrite what a customer paid last week.

Write the schema as SQL you can re-run, and let the constraints do the work described in Relational Database Design and ACID Properties. Two more tables arrive later: one for idempotency keys in milestone 5, and an outbox if you take the stretch goals.

When milestone 2 works, run each query through `EXPLAIN`. A sequential scan is fine over ten rows and not over ten million; add the index the plan asks for rather than the one you guessed. Indexes and Query Optimization read the output.

Common mistake Storing prices as `float` or `money`, or deriving an order's total by joining to the current product price. Both look correct until the catalogue changes.

The contract you must expose

The contract is the part other people build against, so it is the part you cannot quietly change. Fix it before writing handlers.

EndpointDoesAnswers
`GET /health`Liveness. No auth, no database`200`
`POST /v1/auth/register`Creates an account`201`, `409` if the email is taken
`POST /v1/auth/login`Exchanges credentials for a token`200`, `401`
`GET /v1/products`Lists the catalogue, filterable by name`200` with a page
`GET /v1/products/:id`One product`200`, `404`
`POST /v1/orders`Places an order against stock`201`, `409` out of stock, `400` without an idempotency key
`GET /v1/orders`The caller's own orders`200` with a page
`GET /v1/orders/:id`One of the caller's orders`200`, `404`
`PATCH /v1/orders/:id`Cancels an order`200`, `409` once it has shipped

Someone else's order id answers `404`, not `403`, so the response does not confirm the id exists. Authorization explains why that distinction is a security property and not a style choice.

Three rules across every endpoint

  • Every input is validated at the door and every failure uses one shape, the Problem Details format from API Design.
  • Lists are paginated by cursor, never unbounded. Pagination has the query.
  • The path carries the version. API Versioning covers what you may add later without breaking callers.
```http title=the three shapes a caller sees GET /v1/products?limit=20&cursor=1022 200 { "data": [ … ], "nextCursor": 1002 } POST /v1/orders Authorization: Bearer Idempotency-Key: 7c3f1b9e-… 201 { "id": 42, "status": "pending", "total_cents": 1998 } 422 application/problem+json { "title": "Invalid request", "status": 422, "errors": { "quantity": ["Too big: expected <= 99"] } } ```

Common mistake Letting the error shape drift, so one handler returns `{ error }`, another `{ message }` and a third an HTML stack trace. Callers end up parsing all three.

Seven milestones

Build in this order. Each milestone ends in something you can run, because the next one will hide the reason it does not.

  1. Walking skeleton`/health`, configuration read from the environment, one structured log line per request. Deploy it now, while there is nothing in it. Project setup, Environment Variables, Logging
  2. The read pathSchema, a connection pool, `GET /v1/products` with cursor pagination, and the query plans to go with it. SQL, Connection Pooling, Pagination, Indexes
  3. The write path`POST /v1/orders` inside one transaction, decrementing stock. Then prove stock cannot go negative when two customers buy the last unit at once. Transactions, Race Conditions, Atomic Operations
  4. IdentityRegister and login, passwords hashed, a token checked on every request, and orders scoped to their owner. Password Hashing, JWT, Authorization
  5. Exactly onceAn `Idempotency-Key` on `POST /v1/orders`, stored with its response and replayed on a repeat. Back off and retry the calls you make outward. Idempotency, Retries
  6. Work that happens laterMove the confirmation email off the request path onto a queue, with a worker, retries and somewhere for the messages that never succeed. Message Queues, Producer-Consumer Pattern, Dead-Letter Queues
  7. Ship itA container, a pipeline that runs the tests, metrics, a trace id threaded through every log line, and one alert that would have caught milestone 3's bug. Docker, CI/CD, Metrics, Distributed Tracing, Alerts

Milestones 1 and 7 bracket the rest on purpose. A service that is deployed and observable on the first day is the one you can still debug on the last, and leaving both to the end is how a working codebase becomes an unshippable one.

Common mistake Treating milestone 3 as finished because the happy path returns `201`. It is finished when two concurrent requests for one unit of stock produce one order, and you have run that case.

Definition of done

Every requirement in this chapter has a check that passes or fails. A requirement you cannot check is an intention, not a property of your service.

What must holdHow you prove it
Stock never goes negativeFire fifty concurrent orders for the last unit. One returns `201`, the rest `409`, and stock reads zero. Race Conditions
A retry places one orderSend the same `Idempotency-Key` twice. The second call returns the first order and the table gains one row. Idempotency
Orders stay privateRequest another user's order id with a valid token. `404`. Authorization
Bad input is rejectedPost a negative quantity, a string quantity and no body at all. Three `422`s in one shape. API Design
The service outlives its databaseStop PostgreSQL, send traffic, start it again. Requests fail as `503` rather than crashing the process, and recovery needs no restart. Failure Testing, Fault Tolerance
It holds a known loadA load test at a rate you picked, with p95 under a budget you wrote down first. Load Testing, Latency
No secret ships in the imageSearch the built image for your token and find nothing. Secrets Management, Docker
A failure is visibleReintroduce milestone 3's bug on purpose. The alert fires, and a log line names the request that caused it. Alerts, Production Debugging

Write the numbers down before you measure. A latency budget chosen after seeing the result is a description of what you built, not a target it had to meet.

Common mistake Running the load test once, on a laptop, against an empty database. Ten rows fit in memory and every query looks fast; seed the catalogue first.

If you want more

Each of these replaces a simplification you were allowed above with the thing production actually does. Take them one at a time, and keep the checks passing.

  • Serve catalogue reads from a replica, then find the first place a customer can see the lag. Database Replication, Data Consistency
  • Put a cache in front of products, then make it survive every key expiring at once. Caching, Caching Strategies
  • Publish order events through an outbox instead of writing to the queue inside the transaction, and watch the duplicate deliveries arrive. Distributed Transactions, Event-Driven Architecture
  • Rate-limit per user and per IP address, and decide what a shared office network should see. Rate Limiting
  • Partition orders by month, then re-run milestone 2's query plans against the partitioned table. Partitioning
  • Split the worker into its own deployable, and pay every cost Microservices lists. If it is not worth paying, that is the most useful result in this chapter.
