Deployment & Infrastructure

Code that only runs on your laptop helps nobody. This chapter follows the orders API from a Linux server to a container, through an automated pipeline, and onto infrastructure that is itself written as code.

Linux Fundamentals

Almost every backend runs on Linux, including inside containers. You need enough of it to start a service, see what it is doing, and find out why it stopped.

The ideas are ones from Operating Systems: processes and signals, files and permissions, ports. These commands let you inspect each:

QuestionCommand
What is running, and using what?`ps aux`, `top`
Which process listens on which port?`ss -ltnp`
Is the disk full?`df -h`
How much memory is free?`free -h`
Does the service answer locally?`curl -i localhost:3000/health`
What does DNS return?`dig api.shop.com`
What did the service log?`journalctl -u orders-api -f`
Who owns this file, and who may read it?`ls -l`

On a plain server, systemd is the program that starts services at boot, restarts them when they crash and collects their output. A service is described in a unit file:

```ini title=/etc/systemd/system/orders-api.service [Unit] Description=Orders API After=network.target [Service] User=orders WorkingDirectory=/srv/orders-api EnvironmentFile=/etc/orders-api.env ExecStart=/usr/bin/node src/server.ts Restart=on-failure [Install] WantedBy=multi-user.target ``` ```bash sudo systemctl enable --now orders-api # start now and at every boot systemctl status orders-api # running? last exit code? recent log lines ```

Stopping the service sends SIGTERM, which is what the shutdown handler listens for.

Common mistake Running the service as root. A bug that lets an attacker run code then gives them the whole machine. Give the service its own user with access to its own directory only, as `User=orders` does.

Docker

"Works on my machine" happens because machines differ: Node version, system libraries, configuration. Docker packages the app with everything it needs into an image, and the image runs identically anywhere.

  • An image is a read-only package: your code, its dependencies, and a minimal Linux file system.
  • A container is a running instance of an image: an ordinary process, isolated by the kernel so it sees only its own files, network and process list. It is not a virtual machine and starts in milliseconds.
  • A registry stores images so servers can pull them.
```text title=Dockerfile FROM node:26-slim ENV NODE_ENV=production WORKDIR /app COPY package*.json ./ RUN npm ci --omit=dev COPY src ./src USER node EXPOSE 3000 CMD ["node", "src/server.ts"] ```

Each instruction creates a layer, and Docker reuses a layer when its inputs are unchanged. Copying `package*.json` and installing before copying the source means a code change does not reinstall dependencies. There is no build stage because Node runs the TypeScript directly.

```bash docker build -t orders-api:1.4.2 . docker run --rm -p 3000:3000 --env-file .env orders-api:1.4.2 ```

For local development, Compose starts the whole stack with one command:

```yaml title=compose.yaml services: api: build: . ports: ["3000:3000"] environment: DATABASE_URL: postgres://shop:shop@db:5432/shop # service names are hostnames REDIS_URL: redis://cache:6379 depends_on: [db, cache] db: image: postgres:18 environment: { POSTGRES_USER: shop, POSTGRES_PASSWORD: shop, POSTGRES_DB: shop } volumes: ["pgdata:/var/lib/postgresql"] # data outlives the container cache: image: redis:8 volumes: pgdata: ```

Common mistake Starting the app through a shell or `npm start`. That wrapper becomes the container's main process and may not pass SIGTERM on, so every stop is a hard kill after a timeout. Use the list form of `CMD` shown above, which runs `node` directly.

Two more: add a `.dockerignore` listing `node_modules`, `.env` and `.git`, and never put secrets in an image, because anyone who can pull it can read every layer.

Reverse Proxy

A reverse proxy is a server that stands in front of your application, receives every request, and forwards it. Clients talk only to the proxy.

ClientHTTPS →Reverse proxyTLS, routing, limitsHTTP →Node :3000

It takes over work that is common to every app and awkward to do in Node:

  • TLS termination: holds the certificate and decrypts.
  • Routing: `/v1` to the API, `/` to a front-end, by host or path.
  • Buffering: absorbs slow clients so they do not tie up the app.
  • Compression, static files, request size limits, and load balancing across instances.

A forward proxy is the mirror image: it sits in front of clients and hides them from servers. A reverse proxy sits in front of servers.

```text title=nginx: /etc/nginx/conf.d/api.conf upstream orders_api { server 127.0.0.1:3000; keepalive 32; # reuse connections to Node } server { listen 443 ssl; http2 on; server_name api.shop.com; ssl_certificate /etc/letsencrypt/live/api.shop.com/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/api.shop.com/privkey.pem; client_max_body_size 1m; location / { proxy_pass http://orders_api; proxy_http_version 1.1; proxy_set_header Connection ""; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; proxy_read_timeout 30s; } } ```

The `X-Forwarded-*` headers are how Express learns the real client address and scheme, once trust proxy is set. In the cloud, a managed load balancer usually plays this role, and Caddy is a simpler alternative that obtains certificates automatically.

Common mistake Mismatched timeouts. If the proxy gives up after 30 seconds but the app keeps working for 60, the client sees a 504 and retries while the first request is still running. Order them: the app's own limits shortest, then the proxy, then the client.

CI/CD

CI/CD automates the path from a commit to running in production, so that releasing is routine instead of an event.

  • Continuous integration: every push is type-checked and tested automatically. Problems surface minutes after they are written.
  • Continuous delivery: every change that passes becomes a deployable artifact, here a Docker image, and can be released at any time.
  • Continuous deployment: every change that passes is released without a manual step.
Push→Type-check→Test→Build image→Deploy to staging→Smoke test→Deploy to production
```yaml title=.github/workflows/ci.yml name: ci on: push: { branches: [main] } pull_request: jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v6 - uses: actions/setup-node@v6 with: { node-version: 26, cache: npm } - run: npm ci - run: npx tsc # type-check - run: node --test # unit and integration tests (Docker is available for Testcontainers) image: needs: test if: github.ref == 'refs/heads/main' runs-on: ubuntu-latest permissions: { contents: read, packages: write } steps: - uses: actions/checkout@v6 - run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin - run: docker build -t ghcr.io/${{ github.repository }}:${{ github.sha }} . - run: docker push ghcr.io/${{ github.repository }}:${{ github.sha }} ```

The image is tagged with the commit hash. Every release is then traceable to exact code, and rolling back means deploying the previous tag.

RolloutHowTrade-off
RollingReplace instances a few at a timeNo extra capacity. Old and new run together for a while.
Blue-greenBring up a full new set, then switch traffic at onceInstant rollback. Double the capacity during the switch.
CanarySend a small share of traffic to the new version and watchLimits the damage of a bad release. Needs good monitoring.

All three run two versions side by side, which is why schema changes must be compatible with both.

Common mistake Deploying the `latest` tag. Nobody can say which code is running, and there is no previous version to roll back to. Deploy immutable, uniquely tagged images.

Cloud Fundamentals

A cloud provider rents out computers, disks and networks by the hour, through an API. You get capacity in minutes and pay for what you use. Every provider offers the same few building blocks under different names.

Building blockWhat it isAWSGoogle CloudAzure
Virtual machineA server you manageEC2Compute EngineVirtual Machines
Container serviceRuns your image; the provider manages serversECS, App RunnerCloud RunContainer Apps
FunctionsRuns code per event, scales to zeroLambdaCloud Run functionsFunctions
Object storageFiles by keyS3Cloud StorageBlob Storage
Managed databasePostgres with backups, patching and failover handledRDS, AuroraCloud SQLDatabase for PostgreSQL
Managed cacheRedis as a serviceElastiCacheMemorystoreManaged Redis
QueueMessages as a serviceSQSPub/SubService Bus

Three concepts tie them together:

  • Regions and zones. A region is a geographic area. Each has several availability zones, separate data centres. Spreading instances across zones is how you get the independent failures that availability depends on.
  • Private networking. Your resources live in a private network (a VPC) divided into subnets. Only the load balancer sits in a public subnet. App servers and databases sit in private ones, reachable only from inside. Firewall rules (security groups) state which resource may call which, on which port.
  • Identity (IAM). Every call to the cloud API is made by an identity with permissions. A server gets its own role, which is how the secrets example authenticated without a key.

The provider secures the data centres and hardware. Configuration is yours: who can reach what, and who can read what.

Common mistake A database reachable from the internet, with a firewall rule open to `0.0.0.0/0` on port 5432. Automated scanners find it within hours. Databases belong in a private subnet, open only to the app's security group.

Kubernetes

Running a few containers by hand is easy. Running hundreds across many machines, restarting the ones that die and rolling out new versions without downtime, is a job for an orchestrator. Kubernetes is the standard one.

Its model is desired state. You declare what should exist ("three copies of this image, reachable on port 80"). Kubernetes compares that with reality in a continuous loop and fixes any difference: a crashed container is restarted, a dead machine's containers are rescheduled elsewhere.

ObjectPurpose
PodThe smallest unit: one or more containers that run together
DeploymentKeeps N identical pods running and performs rolling updates
ServiceA stable name and address that load-balances across a set of pods
IngressRoutes outside HTTP traffic to services: the reverse proxy
ConfigMap / SecretConfiguration and credentials, injected as environment variables or files
```yaml title=k8s/orders-api.yaml apiVersion: apps/v1 kind: Deployment metadata: { name: orders-api } spec: replicas: 3 selector: { matchLabels: { app: orders-api } } template: metadata: { labels: { app: orders-api } } spec: containers: - name: api image: ghcr.io/shop/orders-api:3f9c2ab # the tag CI pushed ports: [{ containerPort: 3000 }] envFrom: [{ secretRef: { name: orders-api-env } }] resources: requests: { cpu: 250m, memory: 256Mi } # reserved for scheduling limits: { memory: 512Mi } # killed if exceeded readinessProbe: { httpGet: { path: /ready, port: 3000 } } livenessProbe: { httpGet: { path: /health, port: 3000 } } --- apiVersion: v1 kind: Service metadata: { name: orders-api } spec: selector: { app: orders-api } ports: [{ port: 80, targetPort: 3000 }] ``` ```bash kubectl apply -f k8s/ # make the cluster match these files kubectl get pods # what is running kubectl logs deploy/orders-api -f # follow logs kubectl rollout undo deploy/orders-api # go back to the previous version ```

Much of this guide plugs in directly. The probes are the health endpoints. A rolling update sends SIGTERM to old pods, which the shutdown handler catches. An autoscaler can change `replicas` from CPU or request rate.

Common mistake Adopting Kubernetes for one small service. It is a platform to operate, with its own upgrades, networking and failure modes. A managed container service runs an image with far less to learn. Kubernetes pays off with many services and a team to look after it.

Infrastructure as Code

Clicking through a cloud console creates infrastructure nobody can review, reproduce or roll back. Infrastructure as code describes servers, databases and networks in files, kept in git and applied by a tool.

What that gives you: a second environment is the same files with different variables, every change goes through code review, and history shows who changed what and why.

Terraform is the most widely used tool. It is declarative, like Kubernetes: you describe the end state and it works out the steps.

```text title=infra/main.tf resource "aws_s3_bucket" "uploads" { bucket = "shop-uploads-${var.environment}" } resource "aws_db_instance" "orders" { identifier = "orders-${var.environment}" engine = "postgres" engine_version = "18" instance_class = "db.t4g.medium" allocated_storage = 50 multi_az = true # standby replica in another zone username = "shop" manage_master_user_password = true # password generated and kept in Secrets Manager } ``` ```bash terraform plan # show exactly what would be created, changed or destroyed terraform apply # make it so, after you confirm ```

Two concepts explain how it behaves:

  • State. Terraform records what it created in a state file and compares your code against it. A team keeps the state in shared, locked storage so two people cannot apply at once.
  • Drift. If someone changes a resource by hand, reality no longer matches the code. The next `plan` shows the difference.

Alternatives follow the same idea: OpenTofu is an open-source fork of Terraform, and Pulumi and AWS CDK let you write infrastructure in TypeScript.

Common mistake Fixing something in the console "just this once". The code is now wrong, and the next apply either reverts your fix or fails. Make every change through the code. Treat the state file as sensitive too, since it can contain generated passwords.
