Concurrency

Concurrency means several tasks in progress at the same time. Requests overlap on every server, including single-threaded Node, and bugs live in the overlap.

Race Conditions

A race condition is a bug where the result depends on which of two overlapping tasks happens to run first.

The classic shape is check, then act. Suppose a `coupons` table with a `used` flag, and a coupon that should work once:

```ts // Broken: both requests can pass the check before either one writes. const { rows } = await pool.query('SELECT used FROM coupons WHERE code = $1', [code]); if (rows[0].used) throw new Error('Coupon already used'); await pool.query('UPDATE coupons SET used = true WHERE code = $1', [code]); await applyDiscount(orderId); ```
  1. Request AReads `used = false`.
  2. Request BReads `used = false`. A has not written yet.
  3. Request ASets `used = true`, applies the discount.
  4. Request BSets `used = true`, applies the discount again.

The check was true when it ran and stale by the time it was used. Node's single thread does not help: at every `await` the function pauses and other requests run. With several server instances, they run truly in parallel.

Races pass tests, because tests send one request at a time. They show up under real traffic, rarely and without a stack trace. Three fixes follow in this chapter: make the step atomic, take a lock, or let a database constraint reject the loser.

Common mistake "Node is single-threaded, so I have no race conditions." Single-threaded means two lines of JavaScript never run at the same instant. It says nothing about what happens between your `await`s.

Atomic Operations

An operation is atomic when it happens as one indivisible step: no other task can observe or interrupt it halfway. If the check and the write are one step, there is no gap to race in.

You rarely build atomicity. You pick an operation that already has it.

```ts // The coupon, fixed: the WHERE is the check, the SET is the act, in one statement. const result = await pool.query( 'UPDATE coupons SET used = true WHERE code = $1 AND used = false', [code], ); if (result.rowCount === 0) throw new Error('Coupon already used'); await applyDiscount(orderId); ```

Two overlapping requests both run the statement; the database lets exactly one match the row.

NeedAtomic tool
Change a row only if a condition holds`UPDATE … WHERE condition`, then read `rowCount`
Create only if absentA `UNIQUE` constraint with `INSERT … ON CONFLICT DO NOTHING`
Count`SET n = n + 1` in SQL, or `INCR` in Redis
Several statements togetherA transaction

When a person edits data over minutes, you cannot hold anything that long. Use optimistic locking: store a version number, and make the write conditional on it being unchanged since the read.

```ts const result = await pool.query( `UPDATE products SET name = $2, version = version + 1 WHERE id = $1 AND version = $3`, [id, name, versionTheClientRead], ); if (result.rowCount === 0) { res.status(409).json({ title: 'Product was changed by someone else', status: 409 }); return; } ```

Common mistake Reading a value into JavaScript, changing it, and writing it back: `stock = row.stock - 1`. Two requests read 5 and both write 4. Send the arithmetic to the database: `SET stock = stock - 1`.

Mutexes & Locks

Some critical sections cannot be squeezed into one atomic statement, for example "call the payment provider, then record the result". Then you take a lock. A mutex is the simplest one: a single holder at a time.

Which lock depends on who is competing:

CompetitorsLockReleased when
Async tasks in one processIn-process mutexThe task finishes
Transactions on one row`SELECT … FOR UPDATE` (see ACID)The transaction ends
Several server instancesDistributed lock in Redis, or a Postgres advisory lockExplicit release, or expiry

An in-process mutex is a queue of promises. Each caller runs after the previous one settles:

```ts title=src/mutex.ts export class Mutex { #tail: Promise = Promise.resolve(); run(task: () => Promise): Promise { const result = this.#tail.then(task); this.#tail = result.catch(() => {}); // a failed task must not block the queue return result; } } ```

Across servers, the lock has to live somewhere they all see. In Redis, "create this key only if it does not exist" is atomic, which makes it a lock:

```ts const key = `lock:invoice:${orderId}`; const token = crypto.randomUUID(); // proves the lock is ours const acquired = await redis.set(key, token, { condition: 'NX', // only if the key is absent expiration: { type: 'PX', value: 30_000 }, // auto-release after 30 s }); if (!acquired) { res.status(409).json({ title: 'Invoice is already being generated', status: 409 }); return; } try { await generateInvoice(orderId); } finally { // Delete only if the value is still our token (Redis 8.4+; older servers need a Lua script) await redis.delEx(key, { condition: 'IFEQ', matchValue: token }); } ```

The expiry stops a crashed holder from blocking everyone forever. The token stops you deleting a lock that expired and now belongs to someone else.

Common mistake Trusting a lock with an expiry as a hard guarantee. If the work outlasts the 30 seconds, a second holder starts while the first is still running. Use such locks to avoid duplicate work, and keep a database constraint as the final guard for correctness.

Thread Safety

Code is thread-safe when it stays correct if several threads run it at the same time. The danger is always the same: shared mutable state, data that more than one task can change.

Node's main thread gives you a head start. Code between two `await`s runs to completion with nothing interleaved. The equivalent bug appears when state shared between requests is used across an `await`:

```ts // Broken: one variable shared by every request. let currentUser: { id: string }; app.use(async (req, res, next) => { currentUser = await loadUser(req); // request B overwrites this while A is still waiting next(); }); ```

Request A can now act as request B's user. Per-request data belongs on a per-request object, such as `res.locals`. For data that must reach deep code without being passed through every function, `AsyncLocalStorage` gives each request its own store:

```ts title=src/context.ts import { AsyncLocalStorage } from 'node:async_hooks'; const store = new AsyncLocalStorage<{ requestId: string }>(); app.use((_req, _res, next) => { store.run({ requestId: crypto.randomUUID() }, next); // everything this request triggers sees it }); export const requestId = () => store.getStore()?.requestId; ```

Worker threads are safe by default for a different reason: messages are copied, so nothing is shared. The exception is `SharedArrayBuffer`, real shared memory. There, plain operations race and only the `Atomics` functions are safe:

```ts const counter = new Int32Array(new SharedArrayBuffer(4)); Atomics.add(counter, 0, 1); // safe from any thread counter[0]++; // read, add, write: three steps another thread can interleave ```

Common mistake Caches and counters in module-level variables. Within one process they work. With two instances each has its own copy, and the numbers disagree. Shared state belongs in Postgres or Redis.

Producer-Consumer Pattern

One part of the system creates work (the producer) and another does it (the consumer). A queue between them lets each run at its own speed.

Producerroute handlerpush →Queuetake →Consumer 1Consumer 2Consumer 3

Three things follow from the queue:

  • The producer does not wait. The order route responds as soon as the email job is queued.
  • Bursts are absorbed. A spike fills the queue while consumers work through it at a steady rate.
  • Consumers scale separately. If the queue keeps growing, add consumers.

The whole pattern fits in a few lines inside one process:

```ts title=src/job-queue.ts export class JobQueue { #items: T[] = []; #waiting: ((item: T) => void)[] = []; push(item: T) { const consumer = this.#waiting.shift(); if (consumer) consumer(item); // a consumer is idle: hand it over directly else this.#items.push(item); } take(): Promise { const item = this.#items.shift(); if (item !== undefined) return Promise.resolve(item); return new Promise((resolve) => this.#waiting.push(resolve)); // wait for the next push } } ``` ```ts const emails = new JobQueue<{ to: string; orderId: string }>(); // Three consumers for (let i = 0; i < 3; i++) { (async () => { for (;;) { const job = await emails.take(); await sendOrderEmail(job).catch(console.error); } })(); } // Producer, inside the order route emails.push({ to: user.email, orderId: order.id }); res.status(202).json(order); // 202 Accepted: received, still processing ```

A queue with no size limit only moves the overload into memory. A bounded queue pushes back when full, by making the producer wait or rejecting new work. That is the same backpressure idea as streams.

Common mistake Running this in memory in production. A restart loses every queued job, and a second server cannot share the queue. Real systems put the queue in a separate durable service, which is the subject of Message Queues.
