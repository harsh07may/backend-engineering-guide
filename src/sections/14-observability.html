Observability

In production you cannot attach a debugger. Observability is how well you can tell what the system is doing from the outside, using what it emits: logs, metrics and traces.

Logging

A log is a timestamped record of something that happened. Logs answer the detailed question: what exactly occurred for this request?

The earlier chapters used `console.log`. Production logs need three more properties:

  • Structured. Each line is a JSON object, so a log system can filter by field: every line for one order, every error from one route.
  • Levelled. `debug`, `info`, `warn`, `error`. Production runs at `info`, and you lower it when investigating.
  • Correlated. Every line carries a request id, so all lines from one request can be pulled together.
```bash npm i pino pino-http ``` ```ts title=src/logger.ts import { randomUUID } from 'node:crypto'; import pino from 'pino'; import { pinoHttp } from 'pino-http'; export const logger = pino({ level: process.env.LOG_LEVEL ?? 'info', redact: ['req.headers.authorization', 'req.headers.cookie'], // never write credentials }); export const httpLogger = pinoHttp({ logger, genReqId: (req, res) => { const id = req.headers['x-request-id']?.toString() ?? randomUUID(); // reuse the caller's id res.setHeader('x-request-id', id); return id; }, }); ``` ```ts title=src/app.ts app.use(httpLogger); // one line per request, plus req.log for your own orders.post('/', async (req, res) => { // … req.log.info({ orderId: order.id, totalCents: order.total_cents }, 'order placed'); }); const onError: ErrorRequestHandler = (err, req, res, _next) => { req.log.error({ err }, 'unhandled error'); // stack trace goes to the log, not the client res.status(500).json({ title: 'Internal Server Error', status: 500 }); }; ``` ```json {"level":30,"time":1794719000123,"req":{"id":"7c1e…","method":"POST","url":"/v1/orders"},"orderId":"1042","totalCents":1000,"msg":"order placed"} ```

Write logs to standard output and let the platform collect them. The app should not manage log files.

Common mistake Logging secrets and personal data: tokens, passwords, whole request bodies. Logs are copied widely and kept for a long time. Log identifiers such as `orderId` and `userId`, and redact the rest.

Metrics

A metric is a number measured over time: requests per second, error rate, memory in use. Logs describe single events. Metrics describe the whole, cheaply, which makes them the basis for dashboards and alerts.

TypeBehaviourExample
CounterOnly goes upRequests served, orders placed
GaugeGoes up and downConnections in use, queue length
HistogramCounts observations into buckets, so percentiles can be computedRequest duration

For a request-serving system, three metrics per endpoint tell most of the story (the RED method): Rate of requests, Errors, Duration. One histogram with labels gives all three.

The usual setup is Prometheus: the app exposes current values at `/metrics`, and a Prometheus server collects ("scrapes") them every few seconds.

```bash npm i prom-client ``` ```ts title=src/metrics.ts import client from 'prom-client'; import type { RequestHandler } from 'express'; client.collectDefaultMetrics(); // memory, CPU, event loop lag const duration = new client.Histogram({ name: 'http_request_duration_seconds', help: 'HTTP request duration in seconds', labelNames: ['method', 'route', 'status'], buckets: [0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5], }); export const measure: RequestHandler = (req, res, next) => { const stop = duration.startTimer(); res.on('finish', () => { stop({ method: req.method, route: req.route ? req.baseUrl + req.route.path : 'unmatched', // '/v1/orders/:id', not the raw URL status: res.statusCode, }); }); next(); }; export const metricsEndpoint: RequestHandler = async (_req, res) => { res.type(client.register.contentType).send(await client.register.metrics()); }; ``` ```ts title=src/app.ts app.use(measure); app.get('/metrics', metricsEndpoint); // expose on an internal port or path only ```

The library's project now lives under the Prometheus organisation, whose docs call the package `@prometheus-io/client`. The API shown here is the same.

Common mistake Labels with unlimited values, such as a user id or the raw URL. Each distinct combination becomes its own time series, and millions of them exhaust the metrics server. Labels must come from a small fixed set. Per-user detail belongs in logs.

Distributed Tracing

When a request crosses several services, logs and metrics from each one show fragments. A trace joins them: one record of the request's whole journey, with the time spent at every step.

  • A trace is one request end to end, identified by a trace id.
  • A span is one step within it: an HTTP call, a query, a function. Each has a start, a duration and a parent span.
  • Context propagation carries the trace id to the next service in a `traceparent` header, so its spans join the same trace.
```text title=one trace, drawn as a timeline POST /v1/orders 212 ms ├─ auth: verify token 2 ms ├─ postgres: BEGIN … COMMIT 31 ms ├─ POST catalog/v1/reservations 170 ms ← the time went here │ └─ postgres: UPDATE products 158 ms └─ redis: DEL product:7 1 ms ```

OpenTelemetry is the vendor-neutral standard for producing this data. Its Node SDK instruments Express, `pg`, Redis and `fetch` automatically, so you get spans without touching handlers:

```bash npm i @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node @opentelemetry/exporter-trace-otlp-proto ``` ```ts title=src/tracing.ts import { NodeSDK } from '@opentelemetry/sdk-node'; import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'; import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-proto'; const sdk = new NodeSDK({ serviceName: 'orders-api', traceExporter: new OTLPTraceExporter(), // sends to a collector at localhost:4318 by default instrumentations: [getNodeAutoInstrumentations()], }); sdk.start(); ``` ```bash # Tracing must load before the app, so it can wrap the libraries as they are imported node --experimental-loader=@opentelemetry/instrumentation/hook.mjs --import ./src/tracing.ts src/server.ts ```

The loader flag is needed because this project uses ES modules. For a step the libraries cannot see, add a span yourself:

```ts import { trace } from '@opentelemetry/api'; const tracer = trace.getTracer('orders'); const invoice = await tracer.startActiveSpan('generate-invoice', async (span) => { try { return await generateInvoice(orderId); } finally { span.end(); // a span must always be ended } }); ```

Traces go to a backend such as Jaeger or Grafana Tempo, where you search by trace id. Put that id in your logs too and you can jump from a slow trace to its log lines.

Common mistake Losing the trace at an asynchronous boundary. A job placed on a queue starts a new, unrelated trace unless the trace context is put in the message and restored by the worker.

Monitoring

Monitoring is watching the system's health continuously, so that you learn about a problem from your own tools and before your users tell you.

Start with what users experience. Four measurements, the golden signals, describe any service:

SignalQuestionFrom
LatencyHow long do requests take?The duration histogram
TrafficHow much demand is there?Request rate
ErrorsWhat share of requests fail?Rate of 5xx responses
SaturationHow close to full is it?CPU, memory, pool wait, queue depth

With Prometheus collecting the histogram from Metrics, each signal is a short query, shown on a Grafana dashboard:

```text title=PromQL # Traffic: requests per second sum(rate(http_request_duration_seconds_count[5m])) # Errors: share of requests answered with a 5xx sum(rate(http_request_duration_seconds_count{status=~"5.."}[5m])) / sum(rate(http_request_duration_seconds_count[5m])) # Latency: 95th percentile, per route histogram_quantile(0.95, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m]))) ```

Watch from two sides:

  • From inside (white-box): the metrics the app reports. Detailed, but silent if the app cannot be reached at all.
  • From outside (black-box): a synthetic check that calls a real endpoint every minute from another network, as a user would. It catches DNS, certificate and routing failures that inside metrics never see.

Watch dependencies as well: database connections and replication lag, queue depth and the dead-letter queue, certificate expiry dates.

Common mistake Monitoring machines instead of the service. CPU and memory graphs can all look normal while every checkout fails. Lead with the golden signals for the journeys that matter, and use machine metrics to explain them.

Alerts

Nobody watches dashboards at 3 a.m. An alert is a rule that watches a metric and notifies a person when a condition holds. The hard part is deciding what deserves to interrupt someone.

A good alert passes three tests:

  • It reflects user impact. Alert on symptoms (errors, slowness) over causes (high CPU). A cause without a symptom can wait until morning.
  • It is actionable. The person paged can do something about it now.
  • It is rare. If it fires weekly and is ignored, it trains people to ignore the real one. This is alert fatigue.
SeverityMeaningGoes to
PageUsers are affected nowThe on-call engineer's phone
TicketNeeds attention within days: disk at 80%, a certificate expiring next weekThe team's queue
NeitherInteresting but not actionableA dashboard only
```yaml title=alerts/orders-api.yaml groups: - name: orders-api rules: - alert: HighErrorRate expr: | sum(rate(http_request_duration_seconds_count{status=~"5.."}[5m])) / sum(rate(http_request_duration_seconds_count[5m])) > 0.02 for: 5m # must hold for 5 minutes: ignores brief blips labels: { severity: page } annotations: summary: "More than 2% of requests are failing" runbook: "https://wiki.shop.com/runbooks/orders-api-errors" - alert: SlowRequests expr: histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))) > 1 for: 10m labels: { severity: page } ```

Every paging alert should link to a runbook: what the alert means, how to check its scope, and the first steps to try. Thresholds should come from your SLO, so that an alert means "we are using up our allowed failures too quickly".

Common mistake An alert for every metric. A flood of pages hides the one that matters and burns out the people on call. Review alerts regularly, and delete or downgrade any that did not need action.

Production Debugging

Something is wrong in production. You cannot pause it or step through it, and users are affected while you look. The skill is a disciplined order of work and reasoning from evidence the system already emits.

  1. ScopeWhat is failing, for whom, since when? One endpoint or all? One instance or every one?
  2. What changed?A deploy, a config change, a migration, a traffic spike. Most incidents begin with a change.
  3. MitigateStop the harm before understanding it: roll back, add capacity, turn the feature off.
  4. NarrowMetrics say where. Traces say which step. Logs say exactly what.
  5. Test a hypothesisState a cause that explains every symptom and check a prediction it makes.
  6. Fix and learnFix the cause, then write down what happened and what will catch it earlier next time.

Each kind of signal answers a different part of step 4:

SignalNarrows toExample finding
MetricsWhich endpoint or instance, and when it startedp95 of `POST /v1/orders` tripled at 14:02
TracesWhich step inside the requestThe time is in a database call
LogsWhat happened for one request id`40P01` deadlock errors on the stock update

The database can report on itself while it is struggling. This shows what is running now and what each query is waiting for:

```sql SELECT pid, state, wait_event_type, now() - query_start AS running_for, left(query, 80) AS query FROM pg_stat_activity WHERE state <> 'idle' ORDER BY running_for DESC; ```

Many rows waiting on a `Lock` point at lock contention. One query running for minutes points at a missing index or a missing timeout. The bottleneck table maps other symptoms to causes.

Afterwards, write a postmortem: a timeline, the cause, and concrete follow-ups such as a new alert, a test or a guard. Keep it blameless. The question is what allowed the mistake, because that is what you can fix.

Common mistake Restarting first. It often restores service and also destroys the evidence: the heap, the stuck queries, the open connections. If you can afford thirty seconds, capture a heap snapshot or the query above, then restart.
