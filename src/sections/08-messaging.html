Messaging & Background Jobs

Not everything belongs inside the request. Sending email, charging cards and telling other services can happen afterwards, as long as the work is never lost and never done twice.

Message Queues

A message queue is the producer-consumer queue moved out of your process into a durable service called a broker. Producers add messages, workers take them, and messages survive restarts on either side.

The broker's central promise is in how it handles failure. A worker takes a message and must acknowledge it when done. If the worker dies first, the broker hands the message to another worker. So a message is delivered at least once: never lost, occasionally repeated.

The shop already runs Redis, so the simplest broker is BullMQ, a job queue library built on it.

```bash npm i bullmq ``` ```ts title=src/queues.ts import { Queue } from 'bullmq'; export const connection = { host: 'localhost', port: 6379 }; export const emailQueue = new Queue('email', { connection }); ``` ```ts title=src/routes/orders.ts // Producer: queue the job and respond. The request no longer waits on the mail server. await emailQueue.add('order-confirmation', { orderId: order.id, to: user.email }); res.status(201).json(order); ``` ```ts title=src/worker.ts import { Worker } from 'bullmq'; import { connection } from './queues.ts'; // Consumer: a separate process, started with `node src/worker.ts` new Worker( 'email', async (job) => { await sendOrderEmail(job.data.to, job.data.orderId); // returning acknowledges the job }, // throwing marks it failed { connection, concurrency: 5 }, ); ```

The API and the worker are now separate processes. Each can crash, deploy and scale without the other.

Common mistake Putting large payloads in the message. Queue the id and let the worker load the current row. Messages stay small, and the worker never acts on stale data.

Event-Driven Architecture

In a request-driven design, the order code calls email, then inventory, then analytics, and must know about all three. In an event-driven design it announces "an order was placed", and whoever cares reacts.

Orderspublishes→order.placed→ Emailsends confirmationInventoryreserves stockAnalyticscounts revenue

The difference is in the kind of message:

CommandEvent
Says"Do this": `send-email`"This happened": `order.placed`
ReceiversExactly one, known to the senderAny number, unknown to the sender
Named inThe imperativeThe past tense

Delivering one event to many independent subscribers is called publish/subscribe. Adding a fourth reaction means adding a subscriber; the orders code does not change.

An event is a small, self-describing record. Give every one an id and a timestamp:

```ts title=src/events.ts export type OrderPlaced = { id: string; // unique per event: lets consumers spot duplicates type: 'order.placed'; occurredAt: string; // ISO 8601 data: { orderId: string; userId: string; totalCents: number }; }; ```

Publish it through the outbox, so the event is recorded in the same transaction as the order.

What you pay: the flow is no longer visible in one function, subscribers lag by a moment (eventual consistency), and debugging means following an event across services.

Common mistake Events used as disguised commands, where the publisher waits for one particular subscriber to respond. That is a remote call with extra steps. If you need the answer now, call the service directly.

Kafka / RabbitMQ

Both move messages between services, and they are built on opposite models. RabbitMQ is a queue that hands messages out and forgets them. Kafka is a log that keeps them.

RabbitMQKafka
ModelQueues. A message is removed once acknowledged.An append-only log per topic. Messages stay for a retention period.
Who tracks progressThe broker, per messageEach consumer, as an offset: its position in the log
Re-reading old messagesNoYes: move the offset back
RoutingFlexible rules send messages to queues by key or patternConsumers subscribe to whole topics
OrderingPer queuePer partition
FitsBackground jobs, per-message retries and delaysEvent streams, many independent readers, very high volume

Kafka splits each topic into partitions to spread load. Messages with the same key always land in the same partition, which is how you keep one order's events in sequence. Consumers that share a group id divide the partitions among themselves; a different group reads everything again independently.

```bash npm i @confluentinc/kafka-javascript ``` ```ts import { KafkaJS } from '@confluentinc/kafka-javascript'; const kafka = new KafkaJS.Kafka({ kafkaJS: { brokers: ['localhost:9092'] } }); // Producer const producer = kafka.producer(); await producer.connect(); await producer.send({ topic: 'orders', messages: [{ key: event.data.orderId, value: JSON.stringify(event) }], // key keeps an order's events in order }); // Consumer const consumer = kafka.consumer({ kafkaJS: { groupId: 'inventory' } }); await consumer.connect(); await consumer.subscribe({ topics: ['orders'] }); await consumer.run({ eachMessage: async ({ message }) => { await reserveStock(JSON.parse(message.value!.toString())); }, }); ```

This is Confluent's client, which keeps the API of the older `kafkajs` package. `kafkajs` itself is no longer maintained.

Common mistake Adopting Kafka for a job queue. If the need is "run this task later, retry if it fails", BullMQ, RabbitMQ or a cloud queue such as SQS is far less to operate. Kafka earns its cost when several systems need the same stream, or you need to replay history.

Retries

Many failures fix themselves: a dropped connection, a busy server, a deadlock. Trying again is the cheapest fault tolerance there is, provided you retry the right errors at the right pace.

Retry (transient)Do not retry (permanent)
Timeouts, connection resets
HTTP 429, 502, 503, 504
Postgres `40001` and `40P01`		HTTP 400, 401, 403, 404, 422
Validation errors
Bugs: the same input fails the same way

Pace matters as much as selection. If a thousand clients all retry after exactly one second, the recovering service is hit by a thousand requests at once and falls over again. Two rules prevent that:

  • Exponential backoff: double the wait after each failure (200 ms, 400 ms, 800 ms).
  • Jitter: randomise each wait so clients spread out.
```ts title=src/retry.ts import { setTimeout as sleep } from 'node:timers/promises'; export async function retry( work: () => Promise, isTransient: (err: unknown) => boolean, attempts = 4, baseMs = 200, ): Promise { for (let attempt = 1; ; attempt++) { try { return await work(); } catch (err) { if (attempt >= attempts || !isTransient(err)) throw err; await sleep(Math.random() * baseMs * 2 ** attempt); // backoff with full jitter } } } ``` ```ts // Re-run a whole transaction on a serialization failure or deadlock const order = await retry( () => placeOrder(userId, productId, quantity), (err) => ['40001', '40P01'].includes((err as { code?: string }).code ?? ''), ); ```

Queues have this built in. In BullMQ it is two options on the job:

```ts await emailQueue.add('order-confirmation', data, { attempts: 5, backoff: { type: 'exponential', delay: 1000, jitter: 0.5 }, }); ```

Common mistake Retrying an operation that is not safe to repeat. If a payment request times out, the charge may have gone through; a blind retry charges twice. Retries are only safe on idempotent operations.

Dead-Letter Queues

Some messages will never succeed: malformed data, a deleted user, a bug in the handler. Retried forever, such a poison message wastes workers and can block everything behind it. A dead-letter queue (DLQ) is where messages go after their last attempt fails.

Queue→Workerfails, attempts left →Retry with backoff  · fails, none left →Dead-letter queue→Alert, inspect, fix, replay

Moving it aside keeps the main queue flowing and keeps the evidence: the message and its last error. Once the cause is fixed, the messages are replayed into the main queue.

Every broker has the mechanism. RabbitMQ routes rejected messages to a dead-letter exchange, and SQS has a redrive policy. BullMQ keeps exhausted jobs in a "failed" set, and you can copy them to a dedicated queue:

```ts title=src/worker.ts import { Queue, Worker } from 'bullmq'; const deadLetters = new Queue('email-dead', { connection }); const worker = new Worker('email', handler, { connection }); worker.on('failed', async (job, err) => { if (!job || job.attemptsMade < (job.opts.attempts ?? 1)) return; // retries remain await deadLetters.add(job.name, { original: job.data, error: err.message, failedAt: new Date().toISOString(), }); }); ``` ```ts // Replay, after the fix is deployed for (const job of await deadLetters.getJobs(['waiting'])) { await emailQueue.add(job.name, job.data.original, { attempts: 5 }); await job.remove(); } ```

Common mistake A DLQ nobody looks at. It fills silently and customers find the problem first. Alert when it is not empty, and treat each entry as a bug report.

Idempotency

An operation is idempotent when doing it twice has the same effect as doing it once. It is what makes everything else in this chapter safe: clients retry, queues deliver at least once, and duplicates will arrive.

Some operations are idempotent by nature, and you can often choose that form:

Repeats safelyDoes not
`SET status = 'paid'`
`DELETE … WHERE id = 7`
Set stock to 40		`SET balance = balance - 500`
`INSERT` a new order
Send an email

For the rest, the caller attaches an idempotency key, a unique id for this one intended operation, and the server remembers which keys it has completed. For an API, the client generates a UUID and sends it in a header. A retry reuses the same key.

```sql CREATE TABLE idempotency_keys ( key text NOT NULL, user_id bigint NOT NULL, response jsonb, PRIMARY KEY (user_id, key) ); ``` ```ts title=src/routes/orders.ts orders.post('/', async (req, res) => { const key = req.get('idempotency-key'); if (!key) { res.status(400).json({ title: 'Idempotency-Key header is required', status: 400 }); return; } const input = CreateOrder.parse(req.body); const userId = res.locals.user.id; const order = await withTransaction(async (tx) => { // Claim the key. The primary key makes this atomic: only one request can insert it. const claim = await tx.query( 'INSERT INTO idempotency_keys (user_id, key) VALUES ($1, $2) ON CONFLICT DO NOTHING', [userId, key], ); if (claim.rowCount === 0) { // Seen before: return what the first request produced. const seen = await tx.query( 'SELECT response FROM idempotency_keys WHERE user_id = $1 AND key = $2', [userId, key], ); return seen.rows[0].response; } const created = await placeOrderIn(tx, userId, input.productId, input.quantity); await tx.query( 'UPDATE idempotency_keys SET response = $3 WHERE user_id = $1 AND key = $2', [userId, key, created], ); return created; }); res.status(201).json(order); }); ```

`placeOrderIn` is the body of placeOrder with the transaction passed in. Because the key and the order commit together, there is no state where one exists without the other. A duplicate that arrives while the first is still running waits on the insert, then reads the stored response.

Message consumers use the same idea with the event's id: insert it into a `processed_events` table in the same transaction as the work, and skip the message if the insert conflicts.

Common mistake Checking for the key, doing the work, then saving the key. That is the check-then-act race: two duplicates both pass the check. Claim the key first, atomically, as the insert above does.
