Data Storage

Postgres is the source of truth, and it should not hold everything. This chapter adds a cache, a place for files, and a second copy of the database, and looks at what each copy does to correctness.

SQL vs NoSQL

"NoSQL" groups several kinds of database that drop the relational model to get something else: flexible shapes, simpler scaling across machines, or raw speed for one access pattern.

KindData looks likeGood atYou give up
Relational
Postgres, MySQL		Tables with a fixed schemaAd-hoc queries, joins, transactionsSpreading writes across many machines is hard
Document
MongoDB		JSON-like documentsNested data read as a wholeJoins and cross-document rules move into your code
Key-value
Redis, DynamoDB		A key and a valueVery fast lookup by keyQueries by anything other than the key
Wide-column
Cassandra		Rows grouped by a partition keyHuge write volume across many nodesYou design tables around known queries up front

The real question is how you will read the data. If you know every query in advance and they are all "get by key", a key-value store is simpler and scales further. If queries will keep changing, or the data has relationships, start relational.

The line has also blurred. Postgres stores and indexes JSON, which covers the "some fields vary" case without a second database:

```sql ALTER TABLE orders ADD COLUMN metadata jsonb NOT NULL DEFAULT '{}'; SELECT id FROM orders WHERE metadata @> '{"gift": true}'; -- @> means "contains" ```

Common mistake Choosing a NoSQL store "for scale" before any scale exists. You pay the costs on day one (no joins, weaker transactions) for a benefit that one Postgres server would have covered for years.

Redis

Redis is a key-value server that keeps its data in memory, so reads and writes take well under a millisecond. It is the usual home for data that is hot, small and temporary.

Values are more than strings. Each type fits a job:

TypeTypical use
StringCached JSON, counters
HashOne object with fields, such as a session
List / StreamQueues and event logs
SetUnique members, such as users online
Sorted setLeaderboards, rate-limit windows

Two properties make it more than a fast map. Any key can have a TTL and delete itself. And Redis runs commands one at a time, so each command is atomic: two clients calling `INCR` at once always get two different numbers.

```ts title=src/redis.ts import { createClient } from 'redis'; export const redis = await createClient({ url: process.env.REDIS_URL }) // redis://localhost:6379 .on('error', (err) => console.error('redis', err)) .connect(); ``` ```ts await redis.setEx('session:abc123', 3600, JSON.stringify({ userId: '42' })); // expires in 1 hour const session = await redis.get('session:abc123'); // string, or null const views = await redis.incr('views:product:7'); // atomic counter ```

Name keys with a prefix and colons (`session:abc123`) so related keys are easy to find and never collide.

Common mistake Treating Redis as the only copy of data you cannot lose. Memory is finite, and by default a crash can lose the most recent writes. Keep the truth in Postgres, and set a TTL and a memory limit with an eviction policy so Redis sheds old keys instead of refusing writes.

Caching

A cache keeps the result of slow work somewhere fast, so the next request skips the work. It trades freshness for speed: a cached answer may be out of date.

The standard pattern is cache-aside. The application checks the cache first and fills it on a miss.

Request→Redishit →Respond  · miss →Postgres→Store with TTL→Respond
```ts title=src/products.ts import { pool } from './db.ts'; import { redis } from './redis.ts'; export async function getProduct(id: string) { const key = `product:${id}`; const cached = await redis.get(key); if (cached) return JSON.parse(cached); // hit const { rows } = await pool.query( 'SELECT id, name, price_cents, stock FROM products WHERE id = $1', [id], ); if (rows[0]) await redis.setEx(key, 300, JSON.stringify(rows[0])); // miss: fill for 5 minutes return rows[0] ?? null; } export async function renameProduct(id: string, name: string) { await pool.query('UPDATE products SET name = $2 WHERE id = $1', [id, name]); await redis.del(`product:${id}`); // invalidate: next read refills } ```

Two mechanisms keep it honest. Invalidation removes the entry when the data changes. The TTL is the backstop that bounds how stale an entry can get if an invalidation is ever missed.

Redis is one layer. Browsers and CDNs (content delivery networks, servers near the user) cache whole responses when you allow it with a header:

```ts res.set('Cache-Control', 'public, max-age=60').json(product); // anyone may reuse this for 60 s ```

Common mistake Caching per-user data under a shared key or with `public`. One user is then served another's response. Put the user id in the key, and use `Cache-Control: private` or `no-store` for personal data.

What to cache, where, and what happens when a popular key expires is covered in Caching Strategies.

Object Storage

Files such as images, PDFs and video do not belong in database rows or on the app server's disk. Object storage holds them as objects, each a blob with a key, inside a bucket, reached over HTTP.

Amazon S3 defined the model. Google Cloud Storage, Cloudflare R2 and the self-hosted MinIO work the same way, and most accept the S3 API. The database keeps only the object's key and its metadata.

The best upload path skips your server. Your API issues a presigned URL, a short-lived link that permits exactly one operation on one key, and the client sends the file straight to storage.

  1. Client → API"I want to upload a receipt."
  2. API → ClientA key and a presigned URL, valid for five minutes.
  3. Client → Storage`PUT` the file to that URL. Your server never touches the bytes.
  4. Client → API"Done." The API saves the key on the order.
```bash npm i @aws-sdk/client-s3 @aws-sdk/s3-request-presigner ``` ```ts title=src/app.ts import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3'; import { getSignedUrl } from '@aws-sdk/s3-request-presigner'; const s3 = new S3Client({ region: process.env.AWS_REGION }); app.post('/v1/uploads', authenticate, async (_req, res) => { const key = `receipts/${res.locals.user.id}/${crypto.randomUUID()}.pdf`; // we choose the key const command = new PutObjectCommand({ Bucket: process.env.UPLOAD_BUCKET, Key: key, ContentType: 'application/pdf', }); const url = await getSignedUrl(s3, command, { expiresIn: 300 }); // seconds res.status(201).json({ key, url }); }); ```

Common mistake Saving uploads to the server's local disk. A redeploy wipes them, and with two servers the file exists on only one. The related mistake is using the client's filename as the key: names collide, and a crafted name can overwrite someone else's object.

Data Consistency

The moment data has a second copy, such as a cache entry or a replica, a new question appears: after a write, when does every reader see it? Consistency models are the possible answers.

This is a different idea from the C in ACID, which is about constraints inside one database.

ModelPromiseWhere you get it
StrongEvery read returns the latest writeReading the primary database
EventualCopies converge if writes stop; a read may be stale meanwhileCaches, asynchronous replicas
Read-your-writesYou always see your own changes; others may lagSending a user's reads to the primary just after they write

You choose per piece of data, by asking what a stale read costs:

  • Stock at checkout: a stale read oversells. Read the primary, inside the transaction.
  • Product description: a stale read shows old text for a few minutes. A cached copy is fine.
  • "My orders" right after ordering: a stale read looks like a lost order. Needs read-your-writes.

Common mistake The dual write: update Postgres, then update a second system, and assume both happened. If the process dies between them the copies disagree, with nothing to repair them. Keep one source of truth, make the copies disposable (delete the cache key and let the TTL catch misses), and never update a copy first.

Keeping separate services in step is covered in Distributed Transactions.

Database Replication

Replication keeps live copies of the database on other servers. It buys two things: a standby that can take over if the main server dies, and extra servers to answer reads.

App writes→PrimaryWAL stream →Replica 1Replica 2←App reads

One server, the primary, accepts writes. It streams its write-ahead log to replicas, which replay it and serve read-only queries.

Asynchronous (default)Synchronous
Commit returnsAs soon as the primary has itAfter a replica confirms it too
Write speedUnaffectedSlower: each commit waits on the network
If the primary diesThe last few commits may be lostNothing confirmed is lost
Replica readsSlightly behind (replication lag)Can still lag unless configured to wait for replay

In the application, replication shows up as a second pool and a decision per query:

```ts title=src/db.ts export const pool = new Pool({ connectionString: process.env.DATABASE_URL }); // primary export const replica = new Pool({ connectionString: process.env.DATABASE_REPLICA_URL }); // read-only // Can this read be a little stale? -> replica // A write, or a read right after one -> pool ```

Common mistake Writing to the primary and reading the result from a replica in the same request. The replica may be milliseconds behind, so the user saves a change and sees the old value. A second trap: replication is not a backup. A mistaken `DELETE` reaches every replica within moments.

Automatic failover and what happens when servers disagree are covered in Replication in Distributed Systems.
