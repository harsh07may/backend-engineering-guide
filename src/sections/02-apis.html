02 · Building APIs

APIs

An API is a contract: these URLs, these inputs, these outputs. This chapter builds the orders API's contract and the rules that keep it predictable for the people calling it.

REST

REST is a style for HTTP APIs: model your system as resources (nouns such as orders and products), give each a URL, and act on them with the standard HTTP methods.

RequestMeaning
GET /v1/ordersList orders
POST /v1/ordersCreate an order
GET /v1/orders/1042Read one order
PATCH /v1/orders/1042Change part of it
DELETE /v1/orders/1042Remove it
GET /v1/orders/1042/itemsA nested resource: the items of that order

The payoff is predictability. Someone who has seen `/orders` can guess `/products` without reading docs. An Express Router groups the routes of one resource:

```ts title=src/routes/orders.ts import { Router } from 'express'; export const orders = Router(); orders.get('/', listOrders); orders.post('/', createOrder); orders.get('/:id', getOrder); // :id is available as req.params.id orders.patch('/:id', updateOrder); orders.delete('/:id', cancelOrder); ``` ```ts title=src/app.ts import { orders } from './routes/orders.ts'; app.use('/v1/orders', orders); ```

Common mistake Verbs in URLs: `POST /createOrder`, `GET /getOrderById`. The method is already the verb. When an action is not plain create, read, update or delete, name the thing it produces: `POST /v1/orders/1042/refunds`.

HTTP Methods

The method states intent. Two properties decide how clients and proxies may treat a request.

  • Safe: it only reads. Nothing changes on the server.
  • Idempotent: sending it twice leaves the server in the same state as sending it once.
MethodIntentSafeIdempotent
GETReadYesYes
POSTCreate, or trigger an actionNoNo
PUTReplace the whole resourceNoYes
PATCHChange some fieldsNoNot guaranteed
DELETERemoveNoYes

This matters when the network fails mid-request and the client cannot tell whether the server acted. Retrying a GET, PUT or DELETE is harmless. Retrying a POST may create a second order. Making POST retry-safe needs an idempotency key, covered in Idempotency.

PUT sends the full resource, so a missing field means "clear it". PATCH sends only what changes.

Common mistake A GET that changes data, such as `GET /orders/1042/cancel`. Browsers prefetch links, crawlers follow them and caches replay them, so the order gets cancelled by something that only meant to look.

Status Codes

The status code is the outcome in three digits. Clients, proxies and monitoring all act on it before reading the body, so it has to be honest.

CodeMeaningUse it when
200OKA read or update succeeded
201CreatedA POST created something. Add a `Location` header.
204No ContentSuccess with nothing to return, such as a DELETE
400Bad RequestThe request is malformed, such as broken JSON
401UnauthorizedYou have not proven who you are
403ForbiddenWe know who you are and you may not do this
404Not FoundNo such resource
409ConflictClashes with current state, such as a duplicate email
422Unprocessable ContentWell-formed, but fails validation
429Too Many RequestsRate limit hit
500Internal Server ErrorA bug on our side
502 / 503 / 504Bad Gateway / Unavailable / TimeoutUsually sent by the proxy when the app is down or slow

The first digit carries most of the meaning: 2xx worked, 3xx look elsewhere, 4xx the caller must change the request, 5xx the server failed and a retry may help.

```ts res.status(201).location(`/v1/orders/${order.id}`).json(order); // created res.sendStatus(204); // deleted res.status(404).json({ title: 'Order not found', status: 404 }); // missing ```

Common mistake Returning 200 with `{ "error": "…" }` in the body. Retries, alerts and dashboards all read the status, so they record the failure as a success.

API Design

Good design means callers can predict your API. Three habits get most of the way: validate every input at the door, fail in one consistent shape, and name things consistently.

Validate at the door

Everything from the network is untrusted. A Zod schema describes the valid shape; `parse` returns typed data or throws.

```ts title=src/routes/orders.ts import * as z from 'zod'; const CreateOrder = z.object({ productId: z.number().int().positive(), quantity: z.number().int().min(1).max(99), }); orders.post('/', async (req, res) => { const input = CreateOrder.parse(req.body); // throws ZodError if invalid const order = await placeOrder(res.locals.user.id, input.productId, input.quantity); res.status(201).location(`/v1/orders/${order.id}`).json(order); }); ```

`res.locals.user` is set by the authentication middleware and `placeOrder` is written in Transactions.

One error shape

Handlers throw; the single error handler translates. The shape below is Problem Details (RFC 9457), a standard JSON format for HTTP errors.

```ts title=src/app.ts const onError: ErrorRequestHandler = (err, _req, res, _next) => { if (err instanceof z.ZodError) { res.status(422).type('application/problem+json').json({ title: 'Invalid request', status: 422, errors: z.flattenError(err).fieldErrors, // { quantity: ['Too big: …'] } }); return; } console.error(err); res.status(500).type('application/problem+json').json({ title: 'Internal Server Error', status: 500 }); }; ```

Naming

  • Plural nouns for collections: `/orders`, `/orders/1042`.
  • One casing for JSON fields everywhere. This guide uses camelCase in JSON and snake_case in SQL.
  • Timestamps as ISO 8601 in UTC: `2026-11-15T03:47:00Z`. Money as integer minor units: `1999`, not `19.99`.

Common mistake Sending `err.message` or a stack trace to the client. It leaks table names and file paths. Log the detail on the server and return a generic 500.

Pagination

A user with 50,000 orders must not get them in one response. Pagination returns a slice and a way to ask for the next one.

OffsetCursor (keyset)
Request`?limit=20&offset=40``?limit=20&cursor=1022`
SQL`LIMIT 20 OFFSET 40``WHERE id < 1022 LIMIT 20`
Jump to page NYesNo, only next
Deep pagesSlow: the database reads and discards every skipped rowFast at any depth with an index
Rows added meanwhileItems repeat or get skippedStable

Offset suits small admin tables. For feeds and anything large, use a cursor: the client sends back the last id it saw.

```ts title=src/routes/orders.ts const Page = z.object({ limit: z.coerce.number().int().min(1).max(100).default(20), // query values are strings cursor: z.coerce.number().int().positive().optional(), }); orders.get('/', async (req, res) => { const { limit, cursor } = Page.parse(req.query); const { rows } = await pool.query( `SELECT id, status, total_cents, created_at FROM orders WHERE user_id = $1 AND ($2::bigint IS NULL OR id < $2) ORDER BY id DESC LIMIT $3`, [res.locals.user.id, cursor ?? null, limit + 1], // one extra row tells us if more exist ); const data = rows.slice(0, limit); res.json({ data, nextCursor: rows.length > limit ? data.at(-1).id : null }); }); ```

`pool` is the Postgres connection pool from SQL.

Common mistake No upper bound on `limit`. One request for `?limit=10000000` then loads the whole table into memory.

Filtering & Sorting

Clients ask for the subset and order they need through the query string: `GET /v1/orders?status=paid&sort=-created_at`. A leading `-` is a common convention for descending.

The rule that keeps this safe: values go to the database as parameters, and column names come from a fixed allow-list. SQL parameters cannot stand in for column names, so anything outside the list is rejected.

```ts title=src/routes/orders.ts const SORTABLE: Record = { // API name -> real column created_at: 'created_at', total: 'total_cents', }; const Filter = z.object({ status: z.enum(['pending', 'paid', 'shipped', 'cancelled']).optional(), sort: z.string().default('-created_at'), }); orders.get('/search', async (req, res) => { // register before '/:id' const { status, sort } = Filter.parse(req.query); const column = SORTABLE[sort.replace(/^-/, '')]; if (!column) { res.status(400).json({ title: `Cannot sort by "${sort}"`, status: 400 }); return; } const direction = sort.startsWith('-') ? 'DESC' : 'ASC'; const { rows } = await pool.query( `SELECT id, status, total_cents, created_at FROM orders WHERE user_id = $1 AND ($2::text IS NULL OR status = $2) ORDER BY ${column} ${direction} LIMIT 50`, [res.locals.user.id, status ?? null], ); res.json({ data: rows }); }); ```

`column` and `direction` can only ever be strings this file wrote, which is what makes the interpolation safe. In a real API the filter, sort and pagination live in the same list endpoint; they are separate here to keep each idea visible.

Common mistake Putting `req.query.sort` straight into the SQL string. That is SQL injection: the caller can append their own SQL. The attack is covered in SQL Injection.

Authentication

Authentication answers "who is making this request?". Because HTTP is stateless, the proof travels with every request.

CarrierHow it worksTypical client
Session cookieThe server stores the session and the browser sends back its id automaticallyWeb apps
Bearer tokenThe client sends `Authorization: Bearer `. Often a JWT, a signed token the server can verify without a lookup.Mobile apps, other services
API keyA long random secret that identifies an application, not a personServer-to-server

Whichever you choose, the Express shape is the same: one middleware verifies the credential and attaches the identity for later handlers.

```ts title=src/middleware/auth.ts import type { RequestHandler } from 'express'; export const authenticate: RequestHandler = async (req, res, next) => { const token = req.get('authorization')?.match(/^Bearer (.+)$/)?.[1]; const user = token ? await verifyToken(token) : null; // returns { id, role } or null if (!user) { res.status(401).set('WWW-Authenticate', 'Bearer').json({ title: 'Unauthorized', status: 401 }); return; } res.locals.user = user; next(); }; ``` ```ts title=src/app.ts app.use('/v1/orders', authenticate, orders); // every orders route now requires a user ```

`verifyToken` is deliberately left open here. It is written in JWT; Sessions shows the cookie-based alternative.

Common mistake Credentials in the URL, such as `?api_key=…`. URLs are written to access logs, browser history and analytics. Send secrets in a header.

Go deeper: MDN: HTTP authentication

Authorization

Authentication established who you are. Authorization decides what you may do. It needs two separate checks.

  • Role check: may this kind of user call this endpoint at all? Only admins refund orders.
  • Ownership check: may this user touch this particular record? You read your own orders only.
```ts title=src/middleware/auth.ts export const requireRole = (...roles: string[]): RequestHandler => (_req, res, next) => { if (roles.includes(res.locals.user.role)) return next(); res.status(403).json({ title: 'Forbidden', status: 403 }); }; ``` ```ts title=src/routes/orders.ts orders.post('/:id/refunds', requireRole('admin'), refundOrder); // role check orders.get('/:id', async (req, res) => { const { rows } = await pool.query( 'SELECT id, status, total_cents FROM orders WHERE id = $1 AND user_id = $2', // ownership check [req.params.id, res.locals.user.id], ); if (!rows[0]) { res.status(404).json({ title: 'Order not found', status: 404 }); return; } res.json(rows[0]); }); ```

The ownership check lives inside the query, so there is no code path that fetches the order without it. Someone else's order returns 404 and not 403, so the response does not confirm that the id exists.

Common mistake Checking that the user is logged in and then running `WHERE id = $1` alone. Any user can read any order by changing the number in the URL. This is the most common serious API flaw; OWASP calls it broken object level authorization.

Go deeper: OWASP API1: Broken Object Level Authorization

API Versioning

Once other people's code calls your API, you cannot change it freely. Versioning lets you make incompatible changes while old clients keep working.

Safe to ship in placeBreaking: needs a new version
Adding an endpoint
Adding an optional request field
Adding a response field		Removing or renaming a field
Changing a field's type or meaning
Making an optional field required

The common scheme is a version in the path, because it is visible and easy to route. Each version is its own Router:

```ts title=src/app.ts app.use('/v1/orders', authenticate, deprecated, ordersV1); app.use('/v2/orders', authenticate, ordersV2); ```

Retire the old version in the open. Two standard response headers tell clients it is deprecated and when it stops working:

```ts const deprecated: RequestHandler = (_req, res, next) => { res.set({ Deprecation: '@1796083200', // deprecated since 1 Dec 2026 (Unix time) Sunset: 'Wed, 30 Jun 2027 23:59:59 GMT', // stops working after this Link: '; rel="successor-version"', }); next(); }; ```

The alternatives are a version in a header, or dated versions pinned per account as Stripe does. Both keep URLs clean and are harder to test from a browser.

Common mistake Creating v2 for every change. Most changes can be additive. Each live version is code you must keep working, so add fields where you can and version only when you must break.

Go deeper: Stripe: API versioning · RFC 9745: Deprecation header
