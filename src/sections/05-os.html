Operating Systems

Your service is a program the operating system runs, schedules, feeds with I/O and eventually stops. Knowing those mechanics explains most of how Node behaves under load.

Processes

A process is a running instance of a program. The OS gives each one its own private memory and an id (PID), so a crash in one cannot corrupt another.

Because memory is private, processes talk through the OS: sockets, pipes, files. Your API and Postgres are two processes exchanging bytes over a TCP socket.

The OS also talks to processes, through signals:

SignalMeaningCan you handle it?
SIGTERM"Please stop." Sent by deploy tools and container platforms.Yes
SIGINTCtrl+C in a terminalYes
SIGKILLStopped immediately by the OSNo

A deploy sends SIGTERM, waits a grace period, then sends SIGKILL. Use the grace period to finish requests already in flight:

```ts title=src/server.ts import { pool } from './db.ts'; import { redis } from './redis.ts'; const server = app.listen(port); function shutdown() { server.close(async () => { // stop accepting; wait for open requests await pool.end(); await redis.close(); process.exit(0); // exit code 0 = success }); setTimeout(() => process.exit(1), 10_000).unref(); // stuck? give up after 10 s } process.on('SIGTERM', shutdown); process.on('SIGINT', shutdown); ```

Common mistake No SIGTERM handler. Every deploy then cuts off whatever requests were running, and users see random failures that only happen during releases.

Threads

A thread is a path of execution inside a process. Threads in one process share its memory, which makes them cheap to create and fast to coordinate, and is also what makes them dangerous (see Race Conditions).

Many servers use one thread per request. Node does not. Your JavaScript runs on a single main thread that loops over a queue of events: a request arrived, a query finished, a timer fired. This is the event loop.

Main threadyour JavaScript, one piece at a timehands off → OSnetwork sockets Thread pool (4)files, DNS, crypto, zlib Worker threadsyour CPU-heavy code

Waiting is free: while a query is in flight, the main thread serves other requests. Computing is not: a loop that takes 2 seconds stalls every request for 2 seconds. Move such work to a worker thread:

```ts title=src/report-worker.ts import { parentPort, workerData } from 'node:worker_threads'; parentPort!.postMessage(buildReport(workerData)); // heavy CPU work, off the main thread ``` ```ts title=src/reports.ts import { Worker } from 'node:worker_threads'; export function runReport(input: unknown): Promise { return new Promise((resolve, reject) => { const worker = new Worker(new URL('./report-worker.ts', import.meta.url), { workerData: input }); worker.once('message', resolve); worker.once('error', reject); }); } ```

Common mistake Blocking the main thread without noticing: `readFileSync` in a handler, `JSON.parse` on a 50 MB body, synchronous password hashing. One slow request becomes everyone's slow request.

CPU & Memory

CPU is how much computing you can do per second. Memory (RAM) is how much you can hold at once. Running out of either looks different, and the fixes differ.

ResourceWhen it runs outWhat to watch
CPURequests queue behind each other and latency climbsEvent loop lag: how late the loop runs its next task
MemoryThe process is killed (out of memory, OOM)`rss`: total RAM the OS has given the process

Work is I/O-bound when it mostly waits (queries, HTTP calls) and CPU-bound when it mostly computes (image resizing, hashing). Node handles thousands of I/O-bound requests on one core. CPU-bound work needs worker threads or more processes.

```ts import { monitorEventLoopDelay } from 'node:perf_hooks'; const lag = monitorEventLoopDelay({ resolution: 20 }); lag.enable(); setInterval(() => { const { rss, heapUsed } = process.memoryUsage(); console.log({ rssMb: Math.round(rss / 1e6), heapMb: Math.round(heapUsed / 1e6), // JavaScript objects only loopLagP99Ms: Math.round(lag.percentile(99) / 1e6), }); lag.reset(); }, 10_000).unref(); ```

One Node process uses one core for JavaScript. To use eight cores, run eight processes (see Vertical Scaling).

Common mistake Loading everything into memory: reading a 2 GB file with `readFile`, or selecting a million rows into an array. Memory use then scales with data size and the process dies on a big day. Stream it, as the next topic shows.

I/O

I/O (input/output) is any exchange with the world outside the process's memory: disk, network, database. It dominates backend latency because it is so much slower than computing.

OperationRough timeIf a memory read took 1 second
Read from memory100 ns1 second
Read from SSD100 µs17 minutes
Round trip in a data center0.5 ms1.4 hours
Round trip across an ocean150 ms17 days

Blocking I/O makes the thread wait for the result. Non-blocking I/O starts the operation and returns at once; the OS reports back when data is ready. Node is built on the second kind, and `await` is how you write it: the function pauses, the thread moves on.

For large data, do not wait for all of it. A stream delivers it in chunks, and backpressure pauses the source when the destination cannot keep up, so memory stays flat:

```ts import { createReadStream } from 'node:fs'; import { basename } from 'node:path'; import { pipeline } from 'node:stream/promises'; app.get('/v1/exports/:file', async (req, res) => { res.type('text/csv'); // File -> response, a chunk at a time. A slow client slows the read, not the server. await pipeline(createReadStream(`/var/exports/${basename(req.params.file)}`), res); }); ```

Common mistake I/O calls in sequence that could run together. Three independent 50 ms queries awaited one by one take 150 ms; `await Promise.all([a(), b(), c()])` takes 50.

File Systems

A disk is one long run of bytes. The file system turns it into named files in directories, each with an owner, permissions and timestamps.

  • Permissions grant read, write and execute to the owner, a group and everyone else. Run your service as a user that can read only what it needs.
  • File descriptors are the numbered handles a process gets for each open file, and for each socket. The OS caps them per process. Leak them and you hit `EMFILE: too many open files`, which also stops new connections.
  • Writes are buffered. A successful write means the OS has the data in memory, not that it is on disk. `fsync` forces it to disk.

A crash in the middle of a write leaves half a file. The standard fix is to write a temporary file and rename it, because a rename within one file system is atomic: readers see the old file or the new one, never a mix.

```ts import { rename, writeFile } from 'node:fs/promises'; export async function saveAtomically(path: string, data: string) { const tmp = `${path}.${process.pid}.tmp`; await writeFile(tmp, data, { flush: true }); // flush: fsync before closing await rename(tmp, path); // swap in one step } ```

Common mistake Building a path from user input. A request for `../../etc/passwd` walks out of your folder (path traversal). Reduce the input to a bare name with `basename`, as the export route above does, or resolve the full path and check it still starts with your base directory.

Containers add one more rule: their disk is wiped on redeploy. Anything that must last goes to a database or object storage.

Environment Variables

The same code runs on your laptop, in staging and in production. What differs, such as the database URL or the port, is passed in from outside as environment variables: named strings the OS hands a process when it starts.

Node exposes them on `process.env`. Every value is a string, and a missing one is `undefined`. Read them in one place, validate them at startup, and export typed values:

```ts title=src/config.ts import * as z from 'zod'; const Env = z.object({ NODE_ENV: z.enum(['development', 'test', 'production']).default('development'), PORT: z.coerce.number().int().default(3000), DATABASE_URL: z.url(), REDIS_URL: z.url(), }); export const config = Env.parse(process.env); // a bad value stops the app at boot ``` ```bash title=.env (local only) DATABASE_URL=postgres://shop:shop@localhost:5432/shop REDIS_URL=redis://localhost:6379 ```

Locally, `node --env-file=.env` loads the file. In production the platform sets the variables and there is no file.

Common mistake Committing `.env` to git. Once a secret is in history it must be treated as leaked and rotated. Add `.env` to `.gitignore` and commit a `.env.example` with fake values. Where real secrets should live is covered in Secrets Management.

Locks

When two tasks may touch the same resource at once, a lock makes them take turns. One acquires it and proceeds; the rest wait until it is released.

The code that runs while holding the lock is the critical section. The property a lock provides is mutual exclusion: at most one holder at a time.

KindRuleWhere you meet it
ExclusiveOne holder, reading or writingA row during `UPDATE`, or after `SELECT … FOR UPDATE`
Shared / exclusiveMany readers together, or one writer aloneTable locks during schema changes
AdvisoryA named lock with no built-in meaning; the application decides what it protects"Only one server runs this job"

Postgres already locks rows for you inside transactions. Advisory locks cover the cases with no row to lock. Here, several servers start the same nightly job and exactly one proceeds:

```ts import { withTransaction } from './db.ts'; await withTransaction(async (tx) => { const { rows } = await tx.query('SELECT pg_try_advisory_xact_lock(1001) AS acquired'); if (!rows[0].acquired) return; // another server holds it: skip await closeOutDay(tx); }); // released automatically at commit or rollback ```

Locks cost throughput. Waiters sit idle, so hold a lock for as little time and over as little data as possible.

Common mistake A lock that is never released because an error skipped the unlock. Tie the release to something that always happens: the end of a transaction, a `finally` block, or an expiry time.

Locking in application code, across one process and across many servers, is in Mutexes & Locks.

Deadlocks

A deadlock is two tasks each holding a lock the other needs. Neither can continue, and neither will let go.

  1. Order AUpdates product 7. Now holds the lock on row 7.
  2. Order BUpdates product 12. Now holds the lock on row 12.
  3. Order AUpdates product 12. Waits for B.
  4. Order BUpdates product 7. Waits for A. Nothing can move.

Postgres detects the cycle after about a second, aborts one transaction with error `40P01`, and lets the other finish. That is recovery. Prevention is simpler: if every transaction takes its locks in the same order, a cycle cannot form.

```ts // Always lock products in ascending id order, whatever order the cart lists them in. const sorted = items.toSorted((a, b) => a.productId - b.productId); for (const item of sorted) { await tx.query( 'UPDATE products SET stock = stock - $2 WHERE id = $1 AND stock >= $2', [item.productId, item.quantity], ); } ```

Two more defences: keep transactions short so locks are held briefly, and set a ceiling on waiting with `SET lock_timeout = '2s'` so a stuck request fails fast instead of piling up.

Common mistake Treating `40P01` as a bug to swallow. It is a signal to run the whole transaction again from the start (see Retries), and if it happens often, to fix the lock order.
