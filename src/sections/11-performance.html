Performance

Performance work is measurement first. Define what fast means, find where the time or memory actually goes, change one thing, measure again.

Latency

Latency is how long one operation takes, usually the time from request to response. It is what users feel.

Latency is a distribution, so one number hides the story. Use percentiles: p50 is the typical request, p95 and p99 are the slow tail.

MetricMeaningExample
p50 (median)Half of requests are faster40 ms
p951 in 20 is slower than this180 ms
p991 in 100 is slower than this900 ms
AverageBlends both ends into a number nobody experienced75 ms

The tail matters more than it looks. A page that makes 20 API calls will hit a p95-or-worse response on most loads, and your heaviest users make the most requests.

```ts title=src/middleware/latency.ts import { createHistogram } from 'node:perf_hooks'; import type { RequestHandler } from 'express'; export const latency = createHistogram(); export const measure: RequestHandler = (_req, res, next) => { const start = process.hrtime.bigint(); res.on('finish', () => latency.record(Number(process.hrtime.bigint() - start))); // nanoseconds next(); }; // latency.percentile(50) / 1e6 -> p50 in ms // latency.percentile(99) / 1e6 -> p99 in ms ```

Where the time usually goes, and the lever for each:

Time spentLever
Network round tripsFewer calls, connection reuse, servers nearer the user
Waiting on I/O in sequenceRun independent calls in parallel
Repeated workCaching
Slow queriesQuery optimization
Work the user need not wait forA queue

Common mistake Reporting and alerting on the average. It stays calm while one user in a hundred waits ten seconds. Set targets on p95 or p99.

Throughput

Throughput is how much work the system completes per unit of time, such as requests per second. Latency is one request's experience; throughput is the system's capacity.

The two are linked through concurrency, the number of requests in progress at once:

```text concurrency = throughput × latency 200 requests/s × 0.05 s each = 10 requests in flight 200 requests/s × 0.50 s each = 100 in flight (same traffic, ten times the pressure) ```

Every system has a capacity. Below it, latency stays flat as traffic grows. At it, new requests queue, latency climbs steeply and throughput stops rising. Past it, queues grow without bound and throughput can fall as the system spends its effort on requests that will time out anyway.

Light loadlatency flat→Near capacitylatency rising→Saturatedqueues grow, timeouts

Ways to raise throughput: make each request cheaper, add instances (horizontal scaling), or batch, handling many items per round trip. Batching trades a little latency per item for much higher throughput.

A quick local measurement, before the fuller treatment in Load Testing:

```bash npx autocannon --connections 50 --duration 20 http://localhost:3000/v1/products/7 # reports requests/sec and latency percentiles at 50 concurrent connections ```

When load exceeds capacity, protect the system by refusing work early. A fast `503` or `429` is better for everyone than a slow timeout (see Rate Limiting).

Common mistake Quoting throughput without the latency it came with. "5,000 requests per second" at a p99 of eight seconds is a system that has already fallen over. State both: throughput at an acceptable latency.

Profiling

Profiling records where a running program spends its time or memory. It replaces guessing: the slow part is rarely where you expect.

A CPU profile samples the call stack many times per second. Functions that appear in many samples are where the time goes. Node has a profiler built in:

```bash node --cpu-prof --cpu-prof-dir=./profiles src/server.ts # put the server under load, then stop it with Ctrl+C # a .cpuprofile file appears in ./profiles ```

Open the file in Chrome DevTools (Performance panel, Load profile) or in VS Code. It renders as a flame graph:

  • Each box is a function. Its width is the share of time spent in it and everything it called.
  • Boxes stacked on top are the functions it called.
  • Look for wide boxes near the top of a stack: that is code doing the work itself, not waiting on a callee.
QuestionTool
Which function burns CPU?`node --cpu-prof`
What is allocating memory?`node --heap-prof`
What is holding memory?Heap snapshot (see Memory Leaks)
Is the main thread blocked?Event loop lag
Inspect a live process`node --inspect`, then attach DevTools

A CPU profile only shows time spent computing. Time spent waiting on a query does not appear, so for I/O-bound slowness measure the stages instead, as in Bottleneck Identification.

Common mistake Profiling an idle server, or on a laptop with toy data. The profile then shows startup code. Profile under realistic load with realistic data, or sample briefly in production.

Connection Pooling

Opening a database connection costs a TCP handshake, a TLS handshake and a login, and Postgres starts a whole process for it. A pool keeps a few connections open and lends them out, so a query pays none of that.

The pool was created back in SQL. These are the settings that matter under load:

```ts title=src/db.ts export const pool = new Pool({ connectionString: config.DATABASE_URL, max: 10, // connections this instance may open idleTimeoutMillis: 30_000, // close connections unused for 30 s connectionTimeoutMillis: 2_000, // fail fast if none is free within 2 s statement_timeout: 5_000, // Postgres cancels any query running longer than 5 s }); // pool.totalCount, pool.idleCount, pool.waitingCount // waitingCount above 0 means requests are queuing for a connection ```

Sizing is a budget. Postgres accepts a fixed number of connections (100 by default), shared by everything that connects:

```text instances × max < max_connections, with headroom for migrations and admin tools 8 instances × 10 = 80 fits 20 instances × 10 = 200 does not: new connections are refused ```

A bigger pool is not faster. Past a few connections per database core, queries only compete with each other. When instances outgrow the budget, put a pooler such as PgBouncer between them and Postgres. It lets thousands of client connections share a small number of real ones.

The same idea applies to outbound HTTP. Node's `fetch` keeps connections to each host alive and reuses them without configuration.

Common mistake A leaked client: `pool.connect()` on a path that never reaches `release()`. Each leak removes one connection for good. When the last one is gone, every request waits and then times out, while the database looks idle. Keep `release()` in a `finally`, as withTransaction does.

Caching Strategies

Caching introduced cache-aside with a TTL. A strategy answers three further questions: what deserves caching, how the cache stays in step with writes, and what happens when an entry expires under load.

What to cache

Data that is read far more than written, expensive to produce, and tolerable when slightly stale. A product page qualifies. A stock check at checkout does not.

How writes reach the cache

PatternOn a writeTrade-off
Cache-asideUpdate the database, delete the cache keySimple. The next read is a miss.
Write-throughUpdate the database and the cache togetherReads stay warm. Every write pays for the cache too.
Write-behindUpdate the cache now, the database later in batchesVery fast writes. A crash loses what was not yet flushed.

The stampede

When a popular key expires, every request in that instant misses and runs the same slow query at once. Two cheap defences: let only one caller per key do the work, and add randomness to TTLs so keys do not all expire together.

```ts title=src/cache.ts import { redis } from './redis.ts'; const inFlight = new Map>(); export async function cached(key: string, ttlSeconds: number, load: () => Promise): Promise { const hit = await redis.get(key); if (hit) return JSON.parse(hit); let pending = inFlight.get(key) as Promise | undefined; if (!pending) { // first miss does the work pending = load() .then(async (value) => { const jitter = Math.floor(Math.random() * ttlSeconds * 0.1); await redis.setEx(key, ttlSeconds + jitter, JSON.stringify(value ?? null)); return value; }) .finally(() => inFlight.delete(key)); inFlight.set(key, pending); } return pending; // later misses share its result } // const product = await cached(`product:${id}`, 300, () => loadProduct(id)); ```

Storing `null` for a missing row is negative caching. Without it, requests for ids that do not exist reach the database every time. The in-flight map is bounded by design: each entry is removed when its load settles.

When the cache is full

Redis needs a memory limit and an eviction policy. `allkeys-lru` removes the least recently used keys first, which suits a cache.

Common mistake Caching to cover a slow query. The first request after each expiry is still slow, and the slow query now hides until the cache is cold. Fix the query, then cache what is still expensive.

Database Optimization

Query Optimization tuned one query with `EXPLAIN` and indexes. This topic is about the pattern of access: how many queries you send, how much each returns, and how the database is kept healthy.

Fewer round trips

Each query costs a network round trip however small it is. A hundred single-row inserts are a hundred round trips. Send one statement:

```ts // One INSERT for the whole cart: three arrays in, one row per element await tx.query( `INSERT INTO order_items (order_id, product_id, quantity, unit_price_cents) SELECT $1, * FROM unnest($2::bigint[], $3::int[], $4::int[])`, [orderId, items.map((i) => i.productId), items.map((i) => i.quantity), items.map((i) => i.priceCents)], ); ```

On the read side the same idea is the N+1 fix: one query with `ANY($1)` in place of a loop.

Less data per query

  • Name the columns you need. `SELECT *` drags wide columns across the network and blocks index-only plans.
  • Always bound results, with keyset pagination for lists.
  • Precompute heavy aggregates. A dashboard that sums a year of orders on every load should read a small summary table that a background job refreshes.

Protect the database from your own queries

  • Set a `statement_timeout`, as in Connection Pooling, so one runaway query cannot hold a connection for minutes.
  • Keep transactions short. Long ones hold locks and stop Postgres cleaning up old row versions.
  • Send reads that tolerate staleness to a replica.

Maintenance

An `UPDATE` or `DELETE` in Postgres leaves the old row version behind. Autovacuum reclaims that space and refreshes the statistics the planner uses. On tables with heavy churn, check that it keeps up; a table full of dead rows (bloat) makes every scan slower.

Common mistake Adding an index for every slow query. Each one slows every write to that table, and unused ones cost for nothing. Check `pg_stat_user_indexes` for indexes with zero scans and drop them.

Memory Leaks

JavaScript frees memory automatically: the garbage collector removes objects nothing refers to any more. A leak is memory you no longer need but still reference by accident, so the collector must keep it.

The signature is heap usage that rises across hours and never comes back down, ending in an out-of-memory restart. Watch `heapUsed` from CPU & Memory: a healthy process goes up and down around a level; a leaking one climbs.

Usual cause in NodeWhy it leaksFix
A `Map` or object used as a cacheEntries are added and never removedBound it by size or TTL, or use Redis
Event listeners added per requestThe emitter keeps every listener, and whatever each one capturedRemove the listener, or use `once`
Timers never cleared`setInterval` keeps its callback and everything it references`clearInterval` when done
Arrays that only growA module-level log or history listCap the length, or write it elsewhere
```ts // Leak: one entry per user id, forever const profiles = new Map(); app.get('/v1/users/:id', async (req, res) => { if (!profiles.has(req.params.id)) profiles.set(req.params.id, await loadProfile(req.params.id)); res.json(profiles.get(req.params.id)); }); // Leak: a new listener on a shared emitter for every request app.get('/v1/prices', (req, res) => { priceFeed.on('update', (price) => res.write(JSON.stringify(price))); // fix: const onUpdate = …; priceFeed.on('update', onUpdate); // res.on('close', () => priceFeed.off('update', onUpdate)); }); ```

To find one, compare the heap at two points in time:

```ts import { writeHeapSnapshot } from 'node:v8'; process.on('SIGUSR2', () => console.log('heap snapshot:', writeHeapSnapshot())); // kill -USR2 now, again an hour later, then load both files in Chrome DevTools (Memory panel) ```

In the comparison view, sort by what grew. The object type that keeps increasing, and the chain of references keeping it alive, point at the leak.

Common mistake Raising the memory limit or scheduling nightly restarts. Both buy time while the leak keeps growing with traffic. Treat a steadily rising heap as a bug with a specific cause.
