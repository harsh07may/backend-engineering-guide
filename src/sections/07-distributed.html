07 · Scale

Distributed Systems

One server is simple and has a ceiling. Past it you run several machines that must act as one system while any of them, or the network between them, can fail at any moment.

Vertical Scaling

Vertical scaling means giving one server more CPU, memory or faster disk. It is the first move because nothing about the architecture changes.

ForAgainst
No code changes
No distributed-systems problems
Databases benefit directly		A hard ceiling: the biggest machine on offer
Cost grows faster than capacity at the top end
Still one machine: if it dies, everything is down

There is a catch for Node. A bigger machine mostly means more cores, and one Node process runs JavaScript on one of them. To use the rest, run one process per core. The built-in `cluster` module does that and shares a single port among them:

```ts title=src/cluster.ts import cluster from 'node:cluster'; import { availableParallelism } from 'node:os'; if (cluster.isPrimary) { for (let i = 0; i < availableParallelism(); i++) cluster.fork(); cluster.on('exit', () => cluster.fork()); // replace a worker that died } else { await import('./server.ts'); // each worker runs the normal server } ```

On container platforms you skip this and run more one-core containers, which is already horizontal scaling.

Common mistake Reaching for many servers while the database sits on a small machine. Doubling the database's memory is often the cheapest performance fix available. Scale up until it stops being cheap.

Horizontal Scaling

Horizontal scaling means adding more servers that run the same code and sharing requests among them. Capacity grows by adding machines, and losing one is survivable.

It has one requirement: the app must be stateless. Any instance must be able to serve any request, so nothing a later request needs may live in one instance's memory or on its disk.

Breaks with two instancesMove it to
Sessions in a `Map`Redis, or a signed token the client holds
Uploads on local diskObject storage
In-memory cache or countersRedis
An in-process mutexA database lock or distributed lock
`setInterval` jobs (now run on every instance)An advisory lock, or one dedicated worker

The app tier scales out easily once it is stateless. The database does not, because it is the state. It scales through replication and partitioning.

Common mistake Finding hidden state only after adding the second instance: "users get logged out at random" means sessions live in memory. Run two instances in staging from the start so these fail early.

Load Balancing

With several instances, something must decide which one gets each request. A load balancer is a server that accepts all incoming traffic and forwards each request to a healthy instance.

Clients→Load balancer→API 1API 2API 3 failing check: skipped
AlgorithmSends each request toFits
Round robinThe next instance in turnSimilar instances, similar requests
Least connectionsThe instance with the fewest open requestsRequest times that vary a lot
HashThe instance chosen by hashing a key, such as client IPWhen one client should keep hitting one instance

The balancer learns which instances are usable by polling a health check endpoint. Give it two different answers:

```ts title=src/app.ts export const lifecycle = { draining: false }; // server.ts sets this on SIGTERM app.get('/health', (_req, res) => { // liveness: is the process running? res.json({ ok: true }); }); app.get('/ready', async (_req, res) => { // readiness: can it take traffic? if (lifecycle.draining) { res.status(503).json({ ok: false }); return; } try { await pool.query('SELECT 1'); res.json({ ok: true }); } catch { res.status(503).json({ ok: false }); } }); ```

Failing readiness takes the instance out of rotation until it recovers. Failing liveness gets it restarted. During shutdown, failing readiness first lets the balancer stop sending traffic before the process exits.

Common mistake Checking the database in the liveness probe. A short database outage then makes the platform restart every instance at once, and they all come back to a cold start together. Dependencies belong in readiness only.

Replication

Database Replication covered one primary streaming to replicas. The distributed question is what happens when the primary dies, and what other layouts exist.

Failover

A replica must be promoted to primary. Doing it safely requires the surviving nodes to agree on exactly one new leader. If two nodes both believe they are primary (split brain), both accept writes and the data diverges. Systems prevent this with consensus: a node leads only when a majority votes for it, and two majorities cannot exist at once. That is why clusters have odd sizes such as three or five.

Other layouts

LayoutWho accepts writesPrice
Single leaderOne nodeWrites stop briefly during failover
Multi-leaderSeveral, often one per regionTwo leaders can change the same row: conflicts need a resolution rule
LeaderlessAny node; a write succeeds once enough nodes confirm itReaders must reconcile differing copies

Single leader is the default for good reason. Managed Postgres services run the election and promotion for you.

Your part is to survive the switch. Connections to the old primary break, so handle the error instead of crashing, and let the pool reconnect:

```ts title=src/db.ts // An idle pooled connection can fail at any time. With no listener, this error exits the process. pool.on('error', (err) => console.error('postgres connection lost', err)); ```

Common mistake Assuming failover loses nothing. With asynchronous replication, the commits the old primary had not yet shipped are gone. If that is unacceptable for some writes, those need synchronous replication.

Partitioning

Replication copies the same data to more machines. Partitioning, also called sharding, splits the data so each machine holds a different part. It is how you scale writes and storage past one server.

A partition key decides where each row lives:

StrategyRuleGood atRisk
RangeKeys A to M here, N to Z thereRange scans, time-ordered dataUneven load: the newest range gets all the writes
Hash`hash(key) % shards`Even spreadRange queries must ask every shard
```ts import { createHash } from 'node:crypto'; const shards = [poolA, poolB, poolC, poolD]; export function shardFor(userId: string) { const hash = createHash('sha1').update(userId).digest().readUInt32BE(0); return shards[hash % shards.length]; // all of one user's data lives on one shard } ```

The costs are real. A join or transaction across shards is no longer something the database does for you. And with plain modulo, adding a shard moves almost every key; consistent hashing is the technique that moves only a fraction.

Before sharding across servers, Postgres can partition one large table on a single server. Queries on a date range then touch only the matching partitions, and old data is removed by dropping a partition:

```sql CREATE TABLE events ( user_id bigint NOT NULL, created_at timestamptz NOT NULL, payload jsonb NOT NULL ) PARTITION BY RANGE (created_at); CREATE TABLE events_2026_11 PARTITION OF events FOR VALUES FROM ('2026-11-01') TO ('2026-12-01'); ```

Common mistake A partition key that concentrates load. Shard by country and one large country overloads its shard while others idle (a hot partition). Choose a key with many values, evenly used, that most queries already filter by.

Consistency

Data Consistency introduced strong and eventual consistency. In a distributed system the choice is forced on you by one event: a network partition, when nodes are running but cannot reach each other.

During a partition, a node that receives a request has two options. This is the CAP theorem:

ChoiceThe nodeYou getSuits
Consistency (CP)Refuses, because it cannot confirm it has the latest dataErrors, never wrong answersPayments, stock, anything you cannot undo
Availability (AP)Answers with what it hasAnswers that may be stale or conflict laterFeeds, carts, view counts

Partitions are rare, and the trade-off does not vanish between them. Confirming a write with other nodes takes time, so even on a healthy network stronger consistency costs latency.

Leaderless stores expose the dial directly as a quorum. With N copies, a write waits for W of them and a read asks R. If `R + W > N`, every read overlaps at least one node that has the latest write. With N = 3, choosing W = 2 and R = 2 gives up-to-date reads and still tolerates one node down.

A single-primary Postgres setup is a CP choice: if the primary is unreachable, writes fail instead of forking.

Common mistake Reading CAP as "pick two of three". You cannot opt out of network failures. The only real choice is what to do when one happens, and you can make it differently for each kind of data.

Fault Tolerance

With enough machines, something is always broken. A fault-tolerant system keeps working, perhaps with less, when a component fails. The goal is to stop one failure from becoming everyone's failure.

ToolWhat it does
RedundancyMore than one of everything, so no single machine is essential
TimeoutStops waiting on a dependency that has gone quiet
RetryTries again when the failure is likely temporary
Circuit breakerAfter repeated failures, stops calling the dependency for a while and fails immediately
FallbackServes a reduced answer instead of an error

The timeout comes first, because a slow dependency does more harm than a dead one. A dead service fails fast. A slow one holds your requests open until your own connections and memory run out, and then your callers start timing out too. That chain is a cascading failure.

```ts export async function getRecommendations(userId: string): Promise { try { const res = await fetch(`${config.RECS_URL}/users/${userId}`, { signal: AbortSignal.timeout(300), // give up after 300 ms }); if (!res.ok) throw new Error(`recommendations: ${res.status}`); return await res.json(); } catch (err) { console.warn('recommendations unavailable', err); return []; // fallback: the page renders without them } } ```

A circuit breaker wraps a call like this and counts failures. Past a threshold it "opens" and skips the call entirely for a cooling-off period, which spares both your service and the struggling one. Then it lets a trial request through to see whether to close again. In Node, the `opossum` library provides one.

Common mistake Outbound calls with no timeout. `fetch` will wait indefinitely by default, and so will a database query unless you set a limit. Every call that leaves the process needs a deadline.

Distributed Transactions

A transaction is all-or-nothing inside one database. When one operation spans two systems, say the orders database and a payment service, there is no shared `COMMIT`. Either side can succeed while the other fails.

ApproachHowTrade-off
Two-phase commitA coordinator asks every participant to prepare, then tells all to commitTruly atomic, but everyone holds locks while waiting, and a crashed coordinator leaves them stuck
SagaA chain of local transactions. If a step fails, earlier steps are undone by compensating actions, such as a refundNo global locks. Other requests can see the half-finished state.
OutboxWrite the data and a "to be sent" message in one local transaction; a relay delivers the message afterwardsSimple and reliable. The other side learns a moment later.

The outbox is the one to know first. It fixes the dual write: the order and its event are saved together, so an event can never exist without its order or the reverse.

```sql CREATE TABLE outbox ( id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, topic text NOT NULL, payload jsonb NOT NULL, published_at timestamptz ); ``` ```ts // 1. Inside placeOrder's transaction, next to the inserts: await tx.query( 'INSERT INTO outbox (topic, payload) VALUES ($1, $2)', ['order.placed', { orderId: order.rows[0].id, userId }], ); // 2. The relay: a loop in a separate worker process await withTransaction(async (tx) => { const { rows } = await tx.query( `SELECT id, topic, payload FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`, // several relays can run without colliding ); for (const row of rows) await publish(row.topic, row.payload); await tx.query('UPDATE outbox SET published_at = now() WHERE id = ANY($1)', [rows.map((r) => r.id)]); }); ```

If the relay crashes after publishing and before the update, the message goes out again on the next run. Delivery is therefore at least once, and receivers must tolerate duplicates (see Idempotency). `publish` sends to a queue, which is the next chapter.

Common mistake Splitting data that changes together across two services, then needing a distributed transaction to keep it in step. If two things must be atomic, the cheapest answer is usually to keep them in one database.
