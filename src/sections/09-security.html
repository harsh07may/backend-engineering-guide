Security

Every input is written by a stranger, and some strangers are hostile. This chapter covers how to prove who a user is, and the handful of attacks that account for most real breaches.

Password Hashing

Databases leak. If yours holds passwords in readable form, every user's password leaks with it, and people reuse passwords. So you never store the password, only a value derived from it that cannot be turned back.

A hash function is that one-way derivation. At login you hash what the user typed and compare. Two details separate a safe scheme from a broken one:

  • Salt: a random value stored with each hash and mixed into it. Two users with the same password get different hashes, and an attacker cannot use a precomputed table of common passwords.
  • Deliberate slowness: general hashes such as SHA-256 are built for speed, and a graphics card tries billions per second. Password hashes are built to be slow and to need a lot of memory, which makes guessing expensive.

The current recommendation is Argon2id. Node ships it in `node:crypto`. The cost settings below are OWASP's minimum: 19 MiB of memory, 2 passes.

```ts title=src/passwords.ts import { argon2, randomBytes, timingSafeEqual } from 'node:crypto'; import { promisify } from 'node:util'; const derive = promisify(argon2); const cost = { memory: 19_456, passes: 2, parallelism: 1, tagLength: 32 }; // memory in KiB export async function hashPassword(password: string) { const salt = randomBytes(16); const hash = await derive('argon2id', { message: password, nonce: salt, ...cost }); return `${salt.toString('base64')}.${hash.toString('base64')}`; // store this string } export async function verifyPassword(password: string, stored: string) { const [salt, hash] = stored.split('.').map((part) => Buffer.from(part, 'base64')); const attempt = await derive('argon2id', { message: password, nonce: salt, ...cost }); return timingSafeEqual(hash, attempt); // comparison time does not depend on where they differ } ```

Node's docs still mark `crypto.argon2` as a release candidate. The `argon2` package on npm is the long-standing alternative and stores the salt and settings in one string for you.

Common mistake Different login errors for "no such user" and "wrong password". That tells an attacker which emails have accounts. Return one message for both: "Invalid email or password".

Sessions

HTTP forgets you between requests. A session is the server's memory of a logged-in user: after login the server stores a record and gives the browser a random id for it in a cookie. The browser sends the cookie back on every request.

Login OK→Redissess:9f2c… → { userId: 42 }→Set-Cookie: sid=9f2c…→Later requests send the cookie

The id means nothing by itself; all the data stays on the server. Deleting the record logs the user out at once.

```bash npm i express-session connect-redis && npm i -D @types/express-session ``` ```ts title=src/app.ts import session from 'express-session'; import { RedisStore } from 'connect-redis'; import { redis } from './redis.ts'; declare module 'express-session' { interface SessionData { userId: string } // what we keep in the session } app.use(session({ store: new RedisStore({ client: redis }), secret: config.SESSION_SECRET, // signs the cookie so ids cannot be forged name: 'sid', resave: false, saveUninitialized: false, // no session until someone logs in cookie: { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 7 * 24 * 3600 * 1000 }, })); ```
Cookie flagEffect
HttpOnlyJavaScript in the page cannot read the cookie (limits XSS damage)
SecureSent over HTTPS only
SameSite=LaxNot sent on requests started by other sites, except plain link clicks (limits CSRF)
```ts title=src/routes/auth.ts auth.post('/login', async (req, res) => { const { email, password } = Login.parse(req.body); const { rows } = await pool.query('SELECT id, password_hash FROM users WHERE email = $1', [email]); if (!rows[0] || !(await verifyPassword(password, rows[0].password_hash))) { res.status(401).json({ title: 'Invalid email or password', status: 401 }); return; } req.session.regenerate(() => { // new id at login req.session.userId = rows[0].id; res.json({ ok: true }); }); }); auth.post('/logout', (req, res) => { req.session.destroy(() => res.clearCookie('sid').sendStatus(204)); }); ```

Common mistake Keeping the same session id across login. An attacker who planted an id in the victim's browser beforehand is then logged in too (session fixation). `regenerate` issues a fresh id.

JWT

A JSON Web Token carries the user's identity inside the token itself, with a signature that proves the server issued it. The server verifies the signature and needs no lookup.

```text title=three base64url parts, separated by dots eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsInJvbGUiOiJjdXN0b21lciIsImV4cCI6MTc5NDcxOTAwMH0 . 3kF…signature header: {"alg":"HS256"} payload: {"sub":"42","role":"customer","exp":1794719000} ```

The payload's fields are called claims. Standard ones: `sub` (who), `exp` (expiry), `iss` (issuer), `aud` (intended audience). The payload is only encoded, so anyone holding the token can read it. The signature stops them changing it.

This is the `verifyToken` that the authentication middleware left open:

```bash npm i jose ``` ```ts title=src/tokens.ts import { SignJWT, jwtVerify } from 'jose'; const secret = new TextEncoder().encode(config.JWT_SECRET); export function issueToken(user: { id: string; role: string }) { return new SignJWT({ role: user.role }) .setProtectedHeader({ alg: 'HS256' }) .setSubject(user.id) .setIssuedAt() .setExpirationTime('15m') .sign(secret); } export async function verifyToken(token: string) { try { const { payload } = await jwtVerify(token, secret, { algorithms: ['HS256'] }); return { id: payload.sub!, role: payload.role as string }; } catch { return null; // bad signature, expired, or malformed } } ```
SessionJWT
State livesOn the serverIn the token
Per requestOne Redis lookupA signature check, no I/O
Revoke nowDelete the recordNot possible before `exp` without a server-side list
FitsYour own web appSeveral services that must trust one issuer; mobile and API clients

Because a JWT cannot be recalled, keep it short-lived (minutes). Pair it with a refresh token: a long-lived random value stored server-side, which the client exchanges for a new JWT and which you can revoke.

Common mistake Verifying without pinning the algorithm, or putting private data in the payload. Always pass `algorithms`, and treat the payload as public.

OAuth 2.0

OAuth 2.0 lets a user grant your app limited access to their account on another service without giving you their password. "Sign in with Google" is built on it.

RoleIn "Sign in with Google"
Resource ownerThe user
ClientYour app
Authorization serverGoogle's login and consent screens
Resource serverGoogle's APIs holding the user's data

The standard flow is the authorization code flow with PKCE (a one-time proof that the app finishing the flow is the one that started it):

  1. App → BrowserRedirect to Google with your client id, the requested scope, a random `state` and a PKCE challenge.
  2. User → GoogleLogs in and approves. Your app never sees the password.
  3. Google → AppRedirects back to your callback URL with a short-lived `code` and the same `state`.
  4. App → GoogleServer-to-server: exchanges the code, the client secret and the PKCE verifier for tokens.
  5. AppVerifies the ID token, finds or creates the user, starts its own session.
```ts title=src/routes/auth.ts import { createHash, randomBytes } from 'node:crypto'; import { createRemoteJWKSet, jwtVerify } from 'jose'; const googleKeys = createRemoteJWKSet(new URL('https://www.googleapis.com/oauth2/v3/certs')); const redirect_uri = `${config.APP_ORIGIN}/auth/google/callback`; auth.get('/google', (req, res) => { const state = randomBytes(16).toString('base64url'); const verifier = randomBytes(32).toString('base64url'); req.session.oauth = { state, verifier }; // remembered for the callback const url = new URL('https://accounts.google.com/o/oauth2/v2/auth'); url.search = new URLSearchParams({ client_id: config.GOOGLE_CLIENT_ID, redirect_uri, response_type: 'code', scope: 'openid email', state, code_challenge: createHash('sha256').update(verifier).digest('base64url'), code_challenge_method: 'S256', }).toString(); res.redirect(url.href); }); auth.get('/google/callback', async (req, res) => { const saved = req.session.oauth; if (!saved || req.query.state !== saved.state) { // not a flow we started res.status(400).json({ title: 'Invalid OAuth state', status: 400 }); return; } const tokens = await fetch('https://oauth2.googleapis.com/token', { method: 'POST', body: new URLSearchParams({ grant_type: 'authorization_code', code: String(req.query.code), redirect_uri, client_id: config.GOOGLE_CLIENT_ID, client_secret: config.GOOGLE_CLIENT_SECRET, code_verifier: saved.verifier, }), }).then((r) => r.json()); const { payload } = await jwtVerify(tokens.id_token, googleKeys, { issuer: 'https://accounts.google.com', audience: config.GOOGLE_CLIENT_ID, }); req.session.userId = await findOrCreateUser(payload.email as string); res.redirect('/'); }); ```

Strictly, OAuth is about access. The ID token, a JWT describing the user, comes from OpenID Connect, a layer on top. Between services with no user involved, the simpler client credentials grant exchanges an id and secret for a token.

Common mistake Skipping the `state` check. An attacker can then send a victim to your callback with the attacker's own code, and the victim ends up logged in to the attacker's account.

SQL Injection

If user input is pasted into a SQL string, the user is writing part of your query. Input chosen with care changes what the query does.

```ts // Vulnerable: the email becomes part of the SQL text const email = req.body.email; // attacker sends: ' OR '1'='1 await pool.query(`SELECT id FROM users WHERE email = '${email}'`); // What Postgres receives. The condition is now always true: // SELECT id FROM users WHERE email = '' OR '1'='1' ```

With other payloads the same hole reads any table, changes data or drops it. The fix is the one this guide has used since SQL: parameterized queries. The query text and the values travel separately, so a value is never parsed as SQL.

```ts await pool.query('SELECT id FROM users WHERE email = $1', [email]); // safe for any input ```
  • Identifiers cannot be parameters. Column and table names from input go through an allow-list, as in Filtering & Sorting.
  • Limit the blast radius. The app's database user should not own the schema or be a superuser.
  • ORMs and query builders parameterize for you, until you use their raw-SQL escape hatch with a template string.

Common mistake "Sanitizing" input by stripping quotes or keywords. Filters get bypassed, and they corrupt honest data such as the name O'Brien. Parameters make the content of the value irrelevant.

CSRF

Browsers attach your site's cookies to every request to your site, including requests started by a different site. Cross-site request forgery abuses that: a page the victim visits quietly submits a request to your API, and it arrives with the victim's session.

  1. VictimIs logged in to `shop.com`. The session cookie sits in the browser.
  2. VictimOpens `evil.example`, which holds a hidden form posting to `shop.com/v1/orders`.
  3. BrowserSends the POST with the `shop.com` cookie attached.
  4. Shop APISees a valid session and places the order.

It needs two things: cookie-based login and an endpoint that changes state. An API that only accepts `Authorization: Bearer` tokens is not exposed, because the browser does not attach those by itself.

Two defences together cover it. First, the `SameSite=Lax` flag from Sessions, which stops the cookie being sent on cross-site POSTs. Second, check where each state-changing request came from. Browsers report that in the `Sec-Fetch-Site` header, which page scripts cannot forge:

```ts title=src/middleware/csrf.ts import type { RequestHandler } from 'express'; const SAFE = new Set(['GET', 'HEAD', 'OPTIONS']); export const rejectCrossSite: RequestHandler = (req, res, next) => { if (SAFE.has(req.method)) return next(); const site = req.get('sec-fetch-site'); // same-origin | same-site | cross-site | none const origin = req.get('origin'); const allowed = site ? site === 'same-origin' || site === 'none' : !origin || origin === config.APP_ORIGIN; // older browsers: fall back to Origin if (allowed) return next(); res.status(403).json({ title: 'Cross-site request blocked', status: 403 }); }; ```

The older technique is a CSRF token: a secret value the server puts in each form and checks on submit, which the attacker's page cannot know. It still works and many frameworks include it.

Common mistake State-changing GET routes. `SameSite=Lax` still sends cookies when a user follows a link, and the check above skips GET. Keep GET safe and both defences hold.

Rate Limiting

Without a limit, one client can try a million passwords, scrape your catalogue, or simply crowd everyone else out. Rate limiting caps how many requests a client may make in a period and answers the rest with `429 Too Many Requests`.

AlgorithmRuleBehaviour
Fixed windowN requests per clock minuteSimple. Allows a double burst across a window boundary.
Sliding windowN requests in the last 60 secondsSmooth. Slightly more to track.
Token bucketTokens refill at a steady rate; each request spends oneAllows short bursts, enforces the average

Two decisions matter more than the algorithm. What identifies a client: the IP for anonymous traffic, the user or API key once logged in. And where the counters live: with several instances they must be shared, so they go in Redis.

```bash npm i express-rate-limit rate-limit-redis ``` ```ts title=src/middleware/limits.ts import { rateLimit } from 'express-rate-limit'; import { RedisStore } from 'rate-limit-redis'; import { redis } from '../redis.ts'; const store = (prefix: string) => new RedisStore({ prefix, sendCommand: (...args: string[]) => redis.sendCommand(args) }); export const apiLimit = rateLimit({ windowMs: 60_000, limit: 300, // per client, per minute standardHeaders: 'draft-8', // tell clients their remaining quota legacyHeaders: false, store: store('rl:api:'), }); export const loginLimit = rateLimit({ // far stricter where guessing pays off windowMs: 15 * 60_000, limit: 10, store: store('rl:login:'), }); ``` ```ts title=src/app.ts app.use('/v1', apiLimit); app.use('/auth/login', loginLimit); ```

The default client key is `req.ip`, so `trust proxy` must be set correctly (see IP Addresses) or every user appears to share the proxy's address.

Common mistake Limiting login by IP only. An attacker spreads guesses across many addresses. Also count failed attempts per account, and slow down or lock that account.

Secrets Management

Secrets are the values that grant access: database passwords, API keys, signing keys. Managing them means controlling where they live, who can read them, and how fast you can replace one that leaks.

WhereUse forWeakness
Source codeNeverEveryone with repository access has it, forever
`.env` fileLocal developmentPlain text on disk; easy to commit by accident
Platform environment variablesSmall deploymentsNo audit trail, manual rotation
Secrets managerProductionOne more service to depend on

A secrets manager (AWS Secrets Manager, Google Secret Manager, HashiCorp Vault) stores secrets encrypted, decides per service which ones it may read, logs every read, and can rotate them on a schedule. The app fetches what it needs at startup:

```ts title=src/secrets.ts import { GetSecretValueCommand, SecretsManagerClient } from '@aws-sdk/client-secrets-manager'; const client = new SecretsManagerClient({}); // authenticates as the server's own identity: no key in config export async function loadSecret(id: string): Promise { const { SecretString } = await client.send(new GetSecretValueCommand({ SecretId: id })); return JSON.parse(SecretString!); } const db = await loadSecret<{ username: string; password: string }>('prod/orders-api/postgres'); ```

Rules that hold everywhere

  • Least privilege. Each service gets its own credentials with only the access it needs.
  • Separate per environment. A leaked staging key must not open production.
  • Keep them out of logs. Never log whole config objects or request headers.
  • Be able to rotate. If replacing a secret needs a code change, you will put it off when it matters.

Common mistake Deleting a leaked secret from the repository and calling it fixed. It is still in git history and in every clone. The only fix is to rotate it: issue a new one and revoke the old.
